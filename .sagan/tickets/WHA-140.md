## AC

1. `GET /api/sagan/runs?projectId=<projectId>` returns the list of runs/tickets for that project.
2. `GET /api/sagan/runs/:id` returns the run detail with lanes, phases, verdicts, open decisions, evidence refs, and history.
3. Response is project-scoped; no cross-project leak.
4. Unknown project / ticket → 404 or empty list, not 500.
5. Endpoints return enough data for Overview (C2), Inspector (C3), and Pipeline (C4) without additional bespoke endpoints.

## Non-goals

- Linear ticket title/AC fetch (out of sprint).
- Write endpoints (C5 is the only writer and is separate).

## Frontend

**Built** (Nash, on `hermes/sagan-run`):

- `src/sagan/api.ts` — the read model. `listSaganRuns(project)` and
  `getSaganRun(project, ticketId)` over one replay of the project's
  `.sagan/ledger/events.jsonl`, plus `resolveSaganProject(projectId)` and
  `saganLedgerPath(root)`.
- `src/gateway/index.ts` — `GET /api/sagan/runs?projectId=…` and
  `GET /api/sagan/runs/:id?projectId=…`, token-gated and CORS-reflected like
  every route. Read-only; no writer (C5 owns that).
- `src/sagan/ledger.ts` — additive only: `RawEvent` exported and
  `readLedgerEvents()` split out of `readLedger()` (whose behaviour is
  unchanged), so the API replays the ledger through the SAME parser rather
  than growing a second one.
- `src/agent/threads.ts` — `getChatProject(id)`, the read side of
  `upsertChatProject`.
- `src/sagan/api.test.ts` — 16 tests; added to the `npm test` list.

**Key choices**

- **Project resolution.** No new resolver was needed: `projectId` is a
  `project` table row id (the same id `GET /api/agent/projects` hands the UI),
  and `detectSagan()` (B1) already walks a project folder to its repo root.
  So `projectId → project row → detectSagan → root → root/.sagan/ledger/
  events.jsonl`. **No path is ever taken off the wire**, and the `:id` is only
  compared to ticket strings already read out of the file — it never reaches
  the filesystem, so scoping is structural rather than a check that could be
  forgotten. A nested project folder reads its repo root's ledger; a stale id
  resolves to null instead of falling back to the active cwd.
- **The projection stays the only resolver.** Current lane/phase/round/verdict,
  `openDecisions`, `resolvedDecisions` and `decisionHistory` all come from
  WHA-137's `projectLedger` untouched — including the reopened-gate rule. What
  the API adds is the *sequence* the projection collapses: `lanes[]`,
  `verdicts[]`, `evidence[]` and a verbatim `history[]`, each entry carrying
  its ledger line `index` (file order is the only ordering — `ts` is
  day-granular and sometimes absent).
- **`history[]` is verbatim.** Unknown event types are counted in `skipped`
  by the projection but still render as inspector rows, so a Sagan build that
  adds an event type before Conan learns it does not go invisible.
- **Both `evidence.recorded` shapes are kept whole** — verifier runs
  (`sha`/`verifier`/`checks[]`/`overall`/`not_verified`) and producer runs
  (`producer`/`artifacts`, which is an ARRAY on WHA-131 and a STRING on
  WHA-130 in the reference ledger).
- **Ordering** of `runs` is most-recently-touched-first, measured as the last
  ledger LINE the ticket appears on.

**Flagged — AC ambiguities, decided and stated rather than guessed**

1. **The detail route requires `projectId` too.** AC2 writes it as
   `/api/sagan/runs/:id`, but AC3 forbids a cross-project leak, and a ticket
   id alone would have to be searched across every project to be resolved.
   `GET /api/sagan/runs/:id?projectId=…` is the only shape that satisfies both.
2. **No derived status enum.** AC2 names "lanes, phases, verdicts, open
   decisions, evidence refs, history" and C2/C4 say their own labels are up to
   the builder, so the API returns the *facts* those states are computed from
   (lane, phase, round, verdict, `openDecisions`, `needsYou`, evidence) and
   invents no `queued|running|complete|approval|blocked|failed|skipped`
   vocabulary. If C2/C4 would rather share one mapping, that is a small
   follow-up on this module — not a second endpoint.
3. **Known-project-but-not-Sagan is 200, not 404.** Only an unknown
   `projectId` is a 404. A project with no `.sagan/`, a broken overlay, or no
   ledger yet answers `200 {runs: [], project.sagan: {state, reason}}`,
   because C2 AC5 needs empty / malformed-config / error to be *different*
   reachable states and a 404 collapses them into one.
4. **This repo's own ledger yields an empty run list today, correctly.** The
   single line in `.sagan/ledger/events.jsonl` here is a fleet-level
   `run.started` carrying `tickets: [...]` and **no `ticket` key**, so WHA-137
   counts it under `skipped.noTicket` and no run projects from it. That count
   is surfaced in the response. If that fleet-level shape is meant to seed the
   run list, it is a ledger-schema/A2 change, not a B2 one — flagging rather
   than special-casing it here. Against the reference ledger
   (`thewhatmatters/sagan` @ `ab2cb8d`) the list is `WHA-130, WHA-131, T-001`
   with `needsYou = {WHA-130}`.
5. **C3 asks for fields the ledger does not carry** — objective, provider,
   containment, and a read-only transcript. Nothing here fabricates them: the
   API returns every field the ledger *does* record (verbatim, in `history`),
   and C3's "open owning thread/session" target is not derivable from the
   ledger at all, which is consistent with its own AC3 ("only appears when a
   real thread/session target exists"). If those fields must be real, the
   source is the attempt/lineage tables (A1/WHA-136), not this file.
