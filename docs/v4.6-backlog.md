## MCP tab — one-click authenticate / reconnect for unhealthy servers
Today the **MCP HUD tab** (v4.4 US-007) is read-only: it shells `claude mcp list`,
parses each row into `name · status`, and paints a `StatusDot`
(connected→green, `failed`→red, `needs-authentication`/`pending`→amber). When a
server says **"Needs authentication"** or **"Failed to connect,"** the user's only
recourse is to drop into the terminal, run `/mcp`, arrow down to the server, and
trigger the auth flow by hand. That's exactly the "would I otherwise drive a TUI
to fix this?" friction the HUD is supposed to remove.

**The ask:** give each *unhealthy* MCP row an inline **action button** that drives
the fix for the user:
- **`needs-authentication` → "Authenticate"** — kicks off the OAuth flow (which
  opens the system browser for consent); on completion the row flips to
  connected.
- **`failed` → "Reconnect" / "Retry"** — re-runs the health check (a forced
  `claude mcp list`), and *if* the failure is auth-shaped, offers the same
  Authenticate path. (A genuinely-down server or bad URL won't be fixed by
  re-auth — see open questions; the button must not pretend otherwise.)
- **`connected` rows get no action** — nothing to fix.

### The hard constraint (drives the whole design)
**`claude mcp` has no auth subcommand.** Verified against `claude mcp --help`:
the subcommands are `add`, `add-from-claude-desktop`, `add-json`, `get`, `list`,
`remove`, `serve` — **no `auth` / `login` / `connect`.** OAuth authentication for
an MCP server happens **only inside the interactive `/mcp` TUI menu** (select the
server → trigger "Authenticate" → browser opens for consent). So this feature
**cannot shell a one-shot command** — it has to **drive a pty**, the same
keystroke-injection mechanism Conan already uses for the `/context` and `/usage`
refresh and the `/handoff` compact.

Two existing precedents to build on, and the tension between them:
- **Live-pty injection** — `injectContextRefresh` / `injectUsageRefresh` /
  `injectHandoff` (`src/terminal/index.ts`, routed from `src/gateway/index.ts`
  `:573/:603/:615`) inject a slash command into the *correlated* live pty via
  `src/terminal/correlate.ts`. **But the MCP list is account/install-global, not
  session-scoped** (that's the whole reason v4.4 sourced it from `claude mcp list`
  rather than hooks) — so there may be **no correlated session** to inject into,
  and injecting `/mcp` into the user's *working* session hijacks their terminal.
- **Throwaway probe pty** — `src/usage/probe.ts` spawns a short-lived controlled
  `claude` pty, sends a command, captures the frame, and kills it, leaving no
  stray ptys. **This is the better fit:** a dedicated auth pty doesn't touch the
  user's session, matches the global nature of the MCP list, and the probe
  lifecycle (spawn → drive → wait → kill) is already proven.

So the realistic mechanism: **spawn a throwaway `claude` pty, inject `/mcp`,
navigate the menu to the target server, press the Authenticate key, let the
OAuth browser flow run, then poll a forced `claude mcp list` until that server's
status flips (or a timeout).**

### Why it matters
MCP auth tokens expire; "Needs authentication" is a *recurring* state, not a
one-time setup. Making it a one-click fix from the dashboard — without leaving
the HUD or remembering the `/mcp` dance — is high-frequency, screenshot-worthy,
and squarely on the "literacy & orientation in the Claude Code env" thesis. It
turns the MCP tab from a passive status readout into something that *acts*.

### Open questions (resolve at PRD time — at least one needs a spike)
- **TUI navigation is by position, and the menu layout is unverified.** Driving
  `/mcp` means knowing the target server's **row index** and the keypress that
  triggers Authenticate. The `/mcp` menu's exact structure (order, selection
  keys, whether it paginates, what the auth sub-prompt looks like) is **not yet
  captured** — this is the **spike**: record a real `/mcp` session frame-by-frame
  and confirm a deterministic navigation recipe. Order must match (or be mappable
  to) `claude mcp list`'s order, or the index drifts.
- **Completion detection is async and browser-mediated.** OAuth consent happens
  out-of-band in the browser; Conan can't see it directly. Plan: **poll a forced
  `claude mcp list` (`?force=1`) on an interval until the server flips to
  connected**, with a sensible timeout + a "still pending — finish in your
  browser" UI state. (Mirror the probe's bounded-wait discipline so no pty
  leaks if the user abandons the flow.)
- **`failed` ≠ `needs-authentication`.** "Failed to connect" can be a dead server,
  wrong URL, or an expired session that *reads* as failed. The action for `failed`
  should default to **Reconnect (re-health-check)**, and only escalate to
  Authenticate when the failure is auth-shaped. Don't promise auth fixes a
  network failure.
- **Dedicated pty vs. correlated session.** Strong lean: **dedicated throwaway
  pty** (global list, no session hijack). Confirm `/mcp` works in a fresh
  non-interactive-launched `claude` pty (it should — it's a global menu), and that
  the spawned pty inherits the same login/PATH/credentials as the user's
  (`src/usage/probe.ts` already runs through the right shell).
- **Security / consent.** Auth must be an **explicit user click**, never
  auto-fired on detecting `needs-authentication` (it opens a browser + grants an
  OAuth consent). The button is the consent gate. No new route may skip the
  existing token + Origin auth (`src/gateway/auth.ts`) — every new endpoint is
  token-gated like the probe (`/api/claude/usage?probe=1`).
- **Concurrency / debounce.** Block a second auth-pty spawn while one is in
  flight; surface a per-row "authenticating…" state (like the MCP tab's existing
  `checking…` refresh state).

### Rough story breakdown (to refine in the PRD)
1. **Spike: capture the `/mcp` TUI recipe.** Drive `/mcp` in a real pty, record
   the frame sequence, and pin down (a) server ordering vs. `claude mcp list`,
   (b) the keypresses to select a server + trigger Authenticate, (c) the
   post-auth/pending frame. Output: a documented, deterministic navigation
   sequence (or a verdict that it's too brittle and we need a different angle).
2. **Backend: an MCP-auth driver** in `src/mcp/` reusing the throwaway-pty
   lifecycle from `src/usage/probe.ts` — spawn `claude`, inject `/mcp`, run the
   step-1 navigation for a given server name, fire Authenticate, then kill the
   pty. Returns an in-flight handle; never throws; cleans up on timeout/abandon.
3. **Backend: completion polling.** After firing auth, poll forced
   `getMcpServers(true)` (`src/mcp/index.ts`) until the target flips to
   `connected` or a timeout; expose status (`pending` → `connected` / `timeout`).
4. **Route: `POST /api/claude/mcp/:name/authenticate`** (and/or
   `.../reconnect`) — token-gated like the probe; kicks off story 2/3; returns
   the in-flight state. Reconnect = forced re-health-check, escalating to auth
   only when auth-shaped.
5. **UI: inline row action** in `ui/src/components/McpWidget.tsx` — render an
   **Authenticate** button on `needs-authentication` rows and **Reconnect** on
   `failed` rows; per-row in-flight ("authenticating…" / "reconnecting…") state;
   on success the row repaints connected (re-pull via `useMcp` `refresh()`).
   Semantic tokens only; match the existing `↻ refresh` button styling.
6. **Honest UX copy** — make clear Authenticate **opens your browser** for
   consent, and that Reconnect only re-checks health (won't fix a down server).
7. **Verify** via `automate-browser` (light + dark): unhealthy rows show the
   right action; clicking sets the in-flight state; the button is absent on
   connected rows. Native-only note: the actual OAuth browser handoff is verified
   in the built/`tauri dev` app (headless can't complete real OAuth). Typecheck +
   `cd ui && npm run build` clean.

## HUD — unify the secondary toolbar across all tabs (Pulse + Usage get one)
The Skills and MCP HUD tabs each have a **secondary toolbar** — a slim strip
pinned at the top of the panel, *outside* the scroller, with the tab's identity
on the left and its controls on the right:
- **Skills** — a `User (N) / System (N)` group-tab strip (`h-9`, `border-b`).
- **MCP** — `MCP servers · N` on the left, `↻ refresh` on the right (`py-2`,
  `border-b`).

**Pulse and Usage don't follow this pattern, and their controls live in the
wrong place:**
- **Pulse** — its title + the `15m / 1h / 6h / 24h` range selector are baked
  **inside the chart's own header** (`PulseChart.tsx`, the `compact` header
  block), not in a pinned toolbar. They scroll with the chart instead of staying
  put.
- **Usage** — the `↻ /usage` refresh button **already exists** but is threaded
  **into the widget body** via the `refreshBtn` prop (`Widgets.tsx`
  `UsageWidget` `:565-577`, handed down into `LiveUsageView` / the probe face),
  so its position shifts depending on which face renders.

**The ask:** give **Pulse** and **Usage** the same pinned secondary toolbar as
Skills/MCP, so all four HUD tabs share one consistent header chrome:
- **Pulse toolbar** — name **"Pulse"** on the left, the **`15m / 1h / 6h / 24h`
  range selector** on the right (lifted out of the chart's internal header).
- **Usage toolbar** — name **"Usage"** on the left, the **`↻ /usage` refresh
  action** on the right (lifted out of the widget body).

### Why it matters
Consistency is the whole point of a DevTools-style HUD — four tabs that each put
their identity + controls in a different spot reads as four bolt-ons, not one
panel. This is the same "continuous-surface" polish as the v4.5 flush-panel work
(US-014) and the dynamic-toolbar discipline already proven on Skills/MCP. Cheap,
screenshot-worthy, no new data or backend.

### Open questions (resolve at PRD time)
- **Shared component vs. per-widget.** Skills and MCP each own their toolbar
  inline (and own their own `FadeScroll` so it stays pinned). Cleanest path:
  extract a small **`<HudTabHeader>`** (name slot + actions slot, canonical
  height/border/padding) and adopt it in all four tabs — *or* just match the
  existing inline pattern per widget. Recommend the shared component so the four
  toolbars are pixel-identical (one of them — `h-9` Skills vs `py-2` MCP — is
  already slightly off; unify on one spec).
- **Pulse: kill the duplicate header.** With the range selector hoisted into the

- **FadeScroll boundary.** The toolbar must sit **outside** the `FadeScroll`

- **Usage refresh enable-state.** Preserve current behavior: `↻ /usage` injects

  always-visible in the toolbar instead of conditionally rendered in a face.
- **The Context-pressure bar is separate.** The always-on Context %/Compact
  toolbar (`Widgets.tsx` `:319-360`) is a *different* surface (pinned above the
  terminal, not a HUD tab) — out of scope here; don't conflate it with the Usage

## Pulse chart — fix X-axis tick legibility in dark mode (real bug)
The Pulse chart's **X-axis time labels render dark-on-dark in dark mode** (see
the `20:15 … 21:14` axis going nearly invisible on the near-black chart bg).
This **escaped the v4.4 US-005 "Pulse dark-mode axis legibility" fix** — that
pass added the `fill-foreground/70` class but it isn't actually reaching the
tick text.

### Root cause (diagnosed)
In the vendored `ui/src/components/charts/AreaChart.tsx`, the `<XAxis>` (and
`<YAxis>`) set their tick color via a **Tailwind class on the axis element**:
```tsx
fill=""
stroke=""
className={cn("text-xs", "fill-foreground/70")}  // "legible on both light and dark"
```
But Tailwind `fill-*` lands on the axis `<g>`, while **recharts renders each tick
as its own `<text>` element carrying recharts' default `fill` (~`#666`) as an
explicit SVG presentation attribute** — and an attribute set directly on the
element beats an inherited CSS `fill` from the parent `<g>`. So the ticks stay
recharts'-default gray, which reads fine on the light bg but is unreadable on
the dark chart bg. The empty `fill=""` on the axis doesn't override the per-tick
default either.

Compounding it: in the HUD the chart runs **`compact` → `showYAxis={false}`,
`startEndOnly`**, so the **only** axis text visible is exactly the broken
X-axis start/end labels — which is why it's so prominent in the HUD Pulse tab.

### The fix (direction — confirm at PRD time)
Put the theme-token fill **on the tick text itself**, not the axis `<g>`, so it
overrides recharts' per-tick default — e.g. pass it through the `tick` prop
(`tick={{ className: "fill-foreground", transform: "translate(0,6)" }}`) and/or
set `fill="var(--color-foreground)"` on the tick, and drop the empty `fill=""`
that's muddying it. Apply to **both** axes for consistency (Y is hidden in the
HUD but shows in the standalone chart). The token already resolves correctly per
theme — the bug is purely that the value isn't reaching the `<text>`.

### Open questions
- **`fill-foreground/70` vs full `fill-foreground`** — at 70% opacity on the
  dark bg it may still be marginal; check contrast and consider full opacity (or
  a dedicated `--color-chart-axis` token) once it actually applies.
- **Vendored-component edit.** `AreaChart.tsx` is a copy-in Tremor Raw file —
  the fix lives in our vendored copy (fine; that's the convention), just note it
  so a future Tremor re-vendor doesn't silently revert it.
- **Where US-005 went wrong.** Worth a quick look at what v4.4 actually changed
  so the re-fix doesn't repeat the same mistake (class-on-axis instead of
  class-on-tick).

### Rough story breakdown (to refine in the PRD)
1. **Fix the tick fill** in `AreaChart.tsx` so X (and Y) tick text uses the
   foreground token via the `tick` prop, overriding recharts' default; remove the
   conflicting empty `fill=""`.
2. **Verify** via `automate-browser` in **dark mode** (the regression theme):
   the Pulse `15m/1h/6h/24h` start/end labels are clearly legible on the dark
   chart bg; re-check light mode for no regression; check the standalone
   (non-compact) chart's Y-axis too. Typecheck + `cd ui && npm run build` clean.
   Add/refresh the relevant `docs/qa-checklist.md` row so it's caught next time.

### References
- `ui/src/components/charts/AreaChart.tsx` — `<XAxis>` `:681-714` and `<YAxis>`
  `:715-746` (the `fill=""` + `className="fill-foreground/70"` to fix).
- Compact/`startEndOnly` wiring that makes the X labels the only visible axis in

## Settings dialog — drop the search, real tabs, and make the Status tab editable
Three related fixes to the Settings dialog (`SettingsView.tsx`, opened via
Conan ▸ Settings / ⌘,):

**(a) Remove the "Search settings…" input.** The Status tab carries a search box
(`StatusTab`'s `query` state + the filter + the "No settings match" empty
state). The full config is short — a handful of rows — so the search is clutter,
not help. Delete it and render the groups directly.

**(b) Status / Config as real tabs, not a button group.** The two tabs use the
default shadcn segmented `TabsList`/`TabsTrigger` look (the pill/button-group in
the screenshot). Restyle them to **match Conan's own tab design** — the flat,
VS-Code-style tabs with a top-accent active border used by the **terminal tab
strip** and the **HUD tabs** (the `TAB_TRIGGER` class in `Hud.tsx`) — so the app
reads as one consistent chrome instead of three different tab idioms.

**(c) Make the Status tab values editable.** Right now Status is a read-only
mirror and Config is the editable catalog. But **the Status values ARE editable
keys** — `Theme`, `Always thinking`, `Notify after idle (ms)`, `Auto-updates`
are the exact same keys (`theme`, `alwaysThinkingEnabled`,
`messageIdleNotifThresholdMs`, `autoUpdates`) already in the editable
`configSchema()` and already writable via `POST /api/claude/config`
(US-002/US-010). So making Status editable is **almost free**: match each Status
`ConfigEntry` to its schema `KeyType` by `key` and **reuse the existing
`KeyControl` + `save()`** the Config tab already uses (switch / enum-select /
text-number, inline error, re-read on save). **No new backend.**

### Why it matters
The dialog currently shows you your config but makes you go to a *different* tab
to change the very value you're looking at — and three different tab styles
across the app undercut the polished, single-surface feel. This makes Settings
direct (edit where you read) and visually consistent with the rest of Conan.

### Open questions (resolve at PRD time)
- **Does Status-editable make the Config tab redundant?** They'd overlap heavily.
  The remaining distinction: **Status** = currently-*set* values grouped by
  **source scope** (Project/User/Global, where it was read); **Config** = the
  **full catalog** of editable keys (incl. unset ones) grouped by **target file**
  (`settings.json` / `~/.claude.json`). Decide: keep both with that clarified
  framing, or collapse to one tab. (Recommend keeping both for now — smallest
  change, and the by-source vs by-catalog split is genuinely useful.)
- **Write-target scope.** Status groups rows by the scope they were *read* from;
  edits must write to the key's **schema `scope`** (`settings` vs `global`), not
  the display group — matching by `key` already gives the right target, but
  confirm a key read from Project doesn't get written to the wrong file. (Likely
  constrain editing to User/Global-sourced rows, or always write per the schema.)
- **The dialog subtitle lies once Status is editable.** `DialogDescription`
  currently says "…shown here read-only." Update the copy (and carry the Config
  tab's "edits apply on the next Claude session — no live hot-reload" caveat onto
  Status, since the same applies).
- **Rows with no schema match stay read-only.** Any Status entry that isn't an
  editable key (e.g. a CLI-state row) should render as today's read-only
  `code` value — only matched keys get a control.

### Rough story breakdown (to refine in the PRD)
1. **Remove search** — delete the input, `query` state, filter, and the
   no-match empty state from `StatusTab`; render groups directly.
2. **Tab restyle** — point `SettingsView`'s `TabsList`/`TabsTrigger` at the flat
   top-accent tab style shared by `Hud.tsx`/the terminal strip (extract/share the

3. **Editable Status rows** — in `StatusTab`/`ConfigRow`, look up each entry's

4. **Copy fix** — update the dialog subtitle + add the next-session caveat to
   Status.
5. **Verify** via `automate-browser` (light + dark): no search box; tabs match
   the terminal/HUD tab look; editing Theme/Always-thinking/Notify-idle/

## Usage tab — capture the full `/usage` stats (the dropped insights + skills)
The Usage HUD tab renders a `/usage` capture today, but only the **top half**:
the three rate-limit windows (5h / 7d / 7d-Sonnet) and the **Session** block
(cost, API/wall duration, code changes, per-model tokens). The **bottom half of
the `/usage` screen is captured into the frame buffer and then thrown away**:

1. **"What's contributing to your limits usage?"** — the approximate
   attribution insights, e.g. *"73% of your usage came from sessions active for
   8+ hours"* and *"72% of your usage was at >150k context"*, each with its
   explanatory line ("…/compact mid-task, /clear when switching to new tasks").
   **The capture code already waits for the word `"contributing"` as its
   end-of-frame sentinel** (`maybeCaptureUsage` in `src/terminal/index.ts:371`),
   so the section is *in the buffer* — it's just never parsed.
2. **Skills · % of usage** — the per-skill attribution table
   (`/automate-browser 3%`, `/deep-research 1%`).

**The ask:** bring these stats into the Usage tab so it mirrors the full
`/usage` screen, not just the windows + Session block.

### Why it matters
This is the *actionable* half of `/usage` — it tells you **why** your limits are
burning (long background/loop sessions, >150k-context work) and **which skills**
cost the most. For a tool whose whole thesis is "literacy in the Claude Code
env," surfacing the contributing-factors insight in the HUD — instead of making
the user run `/usage` in the terminal and read past the fold — is exactly the
job. (Conan runs lots of long loop sessions; the "8+ hours / >150k" insight is
directly relevant.)

### Open questions (resolve at PRD time)
- **Parse generically, not the two example bullets.** The insights vary —
  Claude may render zero, one, or several, with different thresholds/phrasings.
  Parse them as **(headline %, factor text, detail/advice)** triples rather than
  hardcoding "8+ hours" / ">150k". Same for the skills table: any number of
  `/<skill>  N%` rows.
- **Honest, caveated framing (carry Conan's house style).** The screen itself
  says *"Approximate, based on local sessions on this machine — does not include
  other devices or claude.ai"* and *"Last 24h · independent characteristics, not
  a breakdown."* Preserve that caveat in the UI (matches the existing
  "≈ estimated" / "live · from /usage" honesty), and label the window (Last 24h).
- **Compact rendering in a ~320–460px panel.** The explanatory paragraphs are
  long. Render the headline % + factor prominently and keep the advice text
  small/secondary (or one-line-clamped with the full text in a title/tooltip).
  Skills table = a tidy `name … %` list like the per-model rows.
- **Live-capture only (same as the Session block).** These sections come from a
  live-pty `/usage` capture, not the throwaway probe — so they appear only after
  a capture, exactly like the Session block does now. No probe change.
- **NOT the separate `Stats` tab.** The TUI has a distinct `/stats` screen (the
  "Stats" tab in the screenshot's header). This item is scoped to the **Usage**

## Responsive — dock the HUD to the bottom at narrow widths (don't hide it)
At narrow widths today the HUD **auto-hides** entirely (`hudCrampedHide =
windowWidth < 900` in `App.tsx`, applied as `hidden={!hudOpen || hudCrampedHide}`)
— the reasoning was that a 320px-min HUD can't share *horizontal* space with the
terminal. **The ask:** instead of hiding, **reflow the HUD to the bottom of the
window** so it shares *vertical* space — top region = terminal (+ its Timeline
split) at ~**67%**, bottom region = HUD at ~**33%**, with a **draggable
horizontal divider** so the user can resize. Applies in the narrow view whether
the terminal is alone or the Timeline is open.

So the responsive matrix becomes:
| Width | Layout |
|---|---|
| **Wide (≥900px)** | unchanged — HUD docks **right** (width-resizable, `border-l`, left drag handle); Timeline splits inside `TerminalPane` |
| **Narrow (<900px)** | shell stacks **vertically** — `TerminalPane` on top (~67%), HUD on the **bottom** (~33%, `border-t`, top drag handle, height-resizable); Timeline still overlays the terminal at <720px *within the top region* |

### Why it matters
Hiding the HUD at narrow widths means losing Usage/Pulse/Skills/MCP + the Radio
bar exactly when a smaller window is most likely a secondary/observer window.
Bottom-docking keeps the whole HUD reachable by trading vertical space — the
right move for a tall-but-narrow window.

### The work (this is the big one — multi-story)
The shell root is `flex h-full` (row). `Hud.tsx` is hardcoded **horizontal**:
`style={{ width }}`, `border-l`, a **left** drag handle, `MIN_W`/`MAX_W`, width
persisted in `conan-hud-w`. Bottom-docking needs the HUD to also render
**vertical**: height instead of width, `border-t`, a **top** drag handle,
min/max *height*, height persisted in a new key.

### Open questions (resolve at PRD time)

### Can we enumerate the system's mono fonts? — Yes, but NOT from the webview
This is the crux the user asked about. The honest answer:

- **`window.queryLocalFonts()` (the Local Font Access API) is Chromium-only.**
  Tauri on macOS runs **WKWebView (WebKit)**, which does **not** implement it —
  so it would appear to work in the Vite dev Chrome browser and then **silently
  return nothing/throw in the real shipped app**. Do **not** build on it. (Even
  where it exists, it returns family names, not a monospace flag.)
- **Enumeration must happen gateway-side** (the Node sidecar runs on the user's
  machine and can read the system). Listing *families* is easy (a lib like
  `font-list`, or shelling `system_profiler SPFontsDataType` on macOS /
  `fc-list` on Linux / registry on Windows). **But "monospace only" is not a free
  system call** — you must inspect each font: the authoritative signal is the
  font file's **`post.isFixedPitch`** flag (or the OS/2 PANOSE = monospaced),
  read with a parser like `fontkit`/`opentype.js`; on macOS specifically Core
  Text exposes `kCTFontTraitMonoSpace`, but that needs a native helper. So full
  "mono fonts on this system" = enumerate files → parse → filter `isFixedPitch`.

**Recommended v4.6 scope (ship the pragmatic path; full enumeration later):**
skip system enumeration entirely. Ship a **curated list of common mono fonts**
(Menlo, Monaco, SF Mono, Courier New + popular installs: Geist Mono, JetBrains
Mono, Fira Code, Cascadia Code, Hack, Source Code Pro, IBM Plex Mono) and
**detect which are actually installed** with the **canvas width-measurement
trick** — render a probe string in the candidate font vs. a known fallback and
compare advance widths; a difference means the font is present. **This works in
WKWebView** (no special API), needs no backend, and is fast. The dropdown shows
installed candidates + always the current default; an unknown/uninstalled pick
falls back gracefully via the font stack. **Full gateway enumeration
(`font-list` + `fontkit` `isFixedPitch`) is the documented "better later"
upgrade** if the curated list proves too limiting.

### Open questions (resolve at PRD time)

## Appearance — multiple themes from a config file (beyond light/dark)
Extend the Appearance tab (item #8 — this supersedes its "themes land here
later" note) into a real **multi-theme** system: a **config file** defining
several named themes the user can switch between, beyond today's hardcoded
light/dark pair.

**This fits the existing architecture cleanly.** The whole app palette is ~20
CSS custom properties — `--background`, `--foreground`, `--card`, `--border`,
`--muted(-foreground)`, `--primary(-foreground)`, `--chart-1..5`, `--term-bg`,
`--term-fg`, … — defined on `:root` (light) and overridden under `.dark`
(`ui/src/index.css`). Tailwind v4's `@theme inline` just maps `--color-*` →
`var(--token)`, and `getTerminalTheme()` re-reads `--term-bg/-fg` at call time —
so **the terminal reskins automatically** when tokens change. **A "theme" is
simply a complete value set for those tokens.** Applying one = setting those
custom properties on `document.documentElement` (overriding the `:root` defaults
the `@theme inline` bridge already points at) + toggling `.dark` for the theme's
mode, then nudging the terminal to re-read.

### Shape
- **A theme** = `{ id, name, type: "light" | "dark", tokens: { "--background":
  "#…", … } }`. `type` drives the `.dark` class so Tailwind `dark:` variants and
  `.dark`-scoped CSS still behave.
- **Built-in themes** shipped as bundled JSON in the UI — seed with the current
  Light + Dark, then a few more (e.g. a high-contrast, a couple of popular
  palettes).
- **User themes from a config file** the gateway reads from disk
  (`~/.conan/themes.json` or `~/.conan/themes/*.json`), served via a new
  token-gated route, so a user can add/edit themes by editing the file — *that's*
  the "config file" asked for. Merge user themes over built-ins by `id`.

### Why it matters
Theming is the natural next step for the Appearance tab and the most-requested
kind of personalization. Because Conan already routes everything (incl. the
terminal + charts) through semantic tokens, one theme switch reskins the entire
app coherently — a genuinely good payoff for the existing token discipline.

### Open questions (resolve at PRD time)
- **Relationship to light/dark/auto (the central call).** `useTheme` today is
  `light | dark | auto`. Cleanest: a theme carries a `type`, selecting it sets
  all tokens **and** the `.dark` class; **"auto"** maps to a chosen default-light
  + default-dark theme pair and follows the OS as it does now. The View ▸ Theme
  menu + the toggle adapt to "pick a theme" (grouped by light/dark). Decide this
  before coding — it reshapes `useTheme`, the menu, and persistence
  (`conan-theme` → also a `conan-theme-id`).
- **Partial themes must not break the UI.** A user theme may omit tokens —
  **merge over the built-in default for its `type`** so every required token has
  a value. Define the canonical token key list as the contract.
- **Validate, don't inject raw CSS (security).** Only accept **known token keys**
  with **validated color values** (hex/rgb/hsl) from the disk file — never
  `setProperty` arbitrary keys/values, and never accept raw CSS strings (blocks a
  malicious theme file slipping in `url()`/expressions). The route is token-gated
  like the others; respect `CONAN_DATA_DIR` for the file location (see
  [[conan-live-data-pipeline]] data-dir gotcha).
- **Apply mechanism.** Set the ~20 vars on `documentElement` via
  `style.setProperty` (simplest, live, cooperates with `@theme inline`) vs.
  injecting a `[data-theme]` stylesheet. Lean: setProperty on root. After apply,
  trigger `getTerminalTheme()` re-read on all mounted terminals (same live-apply
  path item #8 needs for the font).
- **Terminal ANSI palette — scope cut.** `getTerminalTheme()` only sets
  bg/fg/cursor; a full terminal theme has 16 ANSI colors. **Out of scope for the
  first cut** (note it) — themes reskin the app chrome + terminal bg/fg, not the
  ANSI 16 yet.
- **Theme *editor* — scope cut.** v4.6 = select among themes + edit the JSON file
  by hand. An in-app theme editor/creator is a later story.
- **Live reload of the file?** Optional `fs.watch` on the themes file → WS
  broadcast (like `tasks`) so edits appear without restart. Nice-to-have; can be
  a follow-up.

### Rough story breakdown (to refine in the PRD)
1. **Theme model + built-ins** — define the token-key contract + a `Theme` type;
   bundle built-in themes (Light, Dark, +a few) in the UI; a `useThemes` hook (or
   extend `useTheme`) that merges built-ins with user themes and exposes the

2. **Apply path** — replace the `.dark`-only `apply()` with: set the theme's

3. **Config-file route** — `GET /api/claude/themes` (token-gated) reading

4. **Appearance-tab selector** — a theme picker (list with palette swatches /
