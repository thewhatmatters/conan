## How Conan detects "a plan is being executed"

**Key point: no new file format, no process-sniffing.** The signal already flows
through the installed hooks → `POST /api/claude/events` (`gateway/index.ts:109`),
which persists to SQLite and broadcasts `{type:'event'}` (`gateway/index.ts:171`).
The forwarder (`scripts/hooks/send-event.mjs`) passes the **full** hook payload
including `tool_input`, so the plan data is already on the wire. v4.3 just reads it.

Three plan sources, in priority order:

### 1. TodoWrite — the live checklist (primary tracker)
Claude Code's `TodoWrite` tool *is* the live plan. Each call replaces the whole
list, so the latest event = the current plan.
- Signal: `PreToolUse`/`PostToolUse` event with `tool_name === "TodoWrite"`.
- Data: `payload.tool_input.todos` = `[{ content, status, activeForm }]`,
  status ∈ `pending | in_progress | completed`.
- Scope: session-specific → correlate to the live pty session (same mechanism the
  Context widget uses) and show only the active session's todos.
- Rehydrate on reload: query the latest `TodoWrite` event for the session from the
  persisted `event` table, so a reconnect restores the current plan.

### 2. ExitPlanMode — the proposed-plan seed (one-shot)
When Claude exits plan mode, it calls `ExitPlanMode` with the proposed plan.
- Signal: event with `tool_name === "ExitPlanMode"`.
- Data: `payload.tool_input.plan` = markdown plan.
- Use: render the markdown as the initial plan view at approval time, then hand
  off to TodoWrite for live per-item progress as execution begins.
- Caveat (be honest in the UI): *entering* plan mode is not a tool call, so the
  only observable signal is the exit. Conan can show "a plan was proposed" but
  cannot reliably show "currently in plan mode."

### 3. Build loop (prd.json) — the dogfooding plan (already captured)
`run-tasks.sh` executing `prd.json` is a plan too, and it's already read +
broadcast as `{type:'tasks'}` (consumed by `useTasks`). "Executing" = the loop is
actively appending to `progress.txt`. Reuse the existing tasks feed; this is a
presentation treatment, not new capture.

## Conditional behavior
The Plan tab is the conditional piece:
- **Show / enable** when the live session has a non-empty TodoWrite list, OR a
  recent `ExitPlanMode` plan, OR an active build loop.
- **Collapse / disable / grey** when there's no active plan, or when all TodoWrite
  items are `completed`.
- Precedence when more than one is present: live TodoWrite → ExitPlanMode seed →
  build-loop plan.

## Observer-effect / refresh cost
The live `/context` capture isn't free: running `/context` injects its full frame
(the category table **plus** the per-tool MCP table and the per-skill table) into
the session, and that output lands in the session's own conversation context. The
tables scale with the number of loaded MCP servers and skills, so a single dump is
on the order of **~4–6k tokens** in a normally-loaded session (more with many MCP
servers). Measured in a real session: two back-to-back `/context` runs grew the
`Messages` category from 30.3k → 42.9k (~12.6k across the span, the two dumps being
the bulk).

**The trap:** the uncommitted US-013 auto-refresh (`autoRefreshContextOnStop`) fires
on every `Stop` hook, throttled to once per 90s per session. Auto-injecting that
often means Conan **inflates the very number it's measuring** and spends the user's
context budget to do it — over a long active session that's tens of thousands of
self-measurement tokens.

**Chosen mitigation for v4.3 — lengthen / adapt the interval (don't refresh every
turn).** Replace the fixed 90s-per-`Stop` cadence with an adaptive trigger that only
auto-injects `/context` when the context has *likely moved a lot* since the last
capture, e.g.:
- Track cumulative output size since the last capture (sum of `PostToolUse`
  `tool_response` sizes + assistant message length on the event stream) and only
  refresh once it crosses a meaningful delta (e.g. a large file read, a big diff,
  a long tool result) — not on small/no-op turns.
- Keep a hard floor between auto-injects (≥ the current 90s) AND a ceiling so it
  still refreshes eventually on a slow session.
- Leave the manual `↻ /context` button and passive capture (parse only when the
  user runs `/context` themselves) as the always-cheap paths; the env gate
  (`CONAN_CONTEXT_AUTOREFRESH=0`) stays as the full off-switch.
- Surface the cost honestly in the UI: the "live · from /context" face should make
  clear that refreshing consumes context, so the user understands the tradeoff.

This keeps the Context widget reasonably fresh while avoiding a refresh on every
turn, so the observation cost tracks *actual* context movement rather than turn
count. (Story-ize this as a refinement of the US-013 auto-refresh in the v4.3 PRD.)

## Settled — `/context` can't fire in a hidden/background window (for the same session)
**Question that prompted this:** when Conan auto-injects `/context`, can it run in
a terminal the user doesn't see, so they aren't confused about why a `/context`
table appeared in their session?

**Answer (settled by reasoning — no research spike needed): no, not for the same
session.** `/context` reports the in-memory state of **one specific `claude`
process** — that exact conversation. That process is the one in the *visible* pty
Conan correlates to. A hidden/background pty would be a **different `claude`
process = a different, fresh conversation**, so its `/context` would read ~0 for
*that* throwaway session, not the numbers for the session the user is working in.
There's no way to attach a second window to an already-running conversation to
interrogate it. (Same reason the throwaway-probe at `/api/claude/usage?probe=1`
works for *global* `/usage` windows — account-wide, identical no matter who asks —
but **cannot** report a *specific* foreground session's context.)

**So the confusion is solved by one of these two instead — not by a hidden window:**
1. **Don't inject at all — compute the breakdown ourselves (preferred).** Conan
   already reads transcript token counts + measures system-prompt / system-tools /
   MCP-tools / memory-files / skills sizes for the on-disk *estimate*
   (`contextBreakdown` in `src/widgets/index.ts`). Tighten that to match the real
   `/context` numbers closely enough and the live inject is unnecessary — nothing
   ever shows in the user's terminal. Open sub-question (small): how close can the
   self-computed breakdown get, and what (if anything) is unknowable without the
   live command.
2. **Bracket the inject in the alternate-screen buffer** (VT `?1049h`/`?1049l`, or
   save/restore + clear) so the `/context` frame renders to a throwaway screen
   Conan scrapes then discards, leaving the user's scrollback untouched. This is
   the *only* part still genuinely uncertain — `claude`'s own TUI controls the
   screen, so whether the injected command's render can be cleanly bracketed needs
   a small spike. Fold the outcome into the adaptive-refresh story above.

References: `src/usage/probe.ts` (probe + parsers), the `contextBreakdown`
estimator in `src/widgets/index.ts`, `src/context/index.ts` (live capture), and the
data-source verdict in CLAUDE.md / memory.

## Context-pressure action bar — conditional "checkpoint & compact" in the HUD tab
When a HUD tab's underlying state crosses a pressure threshold (the motivating case:
the **Context** tab when usage is high), conditionally reveal a **bottom-positioned
action bar** with two actions: **Cancel** (dismiss the bar) and **Compact**
(checkpoint the session). It stays hidden until the threshold is crossed, so it's
out of the way until it's useful.

**Trigger (Context tab):** reuse the `ctxPct` the Context widget already computes;
show the bar when `ctxPct >=` a threshold (suggest **80%**, matching the existing
destructive-ring threshold). `Cancel` hides it until the next higher threshold (so
it doesn't nag every render). The pattern is generic enough to reuse on other tabs
later (e.g. a Usage-window-near-limit bar), but Context is the v4.3 case.

**What "Compact" does — and the key constraint.** Conan **cannot author the handoff
itself**: it observes the session, it doesn't hold the conversation. The handoff
must be written *by the Claude session*, which has the context. So `Compact` uses
the existing **keystroke-injection path** (the same one US-009/010 use for
`/context`//`/usage`) to inject into the correlated pty:
1. `/handoff` — invokes Claude's `handoff` skill, which writes **`HANDOFF.md`**
   (resume-ready session checkpoint).
2. *(optional, then)* `/compact` — Claude Code's built-in conversation compaction,
   to actually reclaim the context the bar was warning about.

**Write target — `HANDOFF.md`, NOT `CLAUDE.md` (decided).** `CLAUDE.md` is
auto-loaded into every future session, so writing session state there bloats it
permanently and pollutes all later sessions — exactly wrong when the goal is to
*relieve* context pressure. `HANDOFF.md` is the purpose-built, read-once checkpoint
the `handoff` skill already produces. (If the session has no live correlated pty,
the bar's `Compact` is disabled/hidden — there's nothing to inject into.)

**Honest UI:** label the action so it's clear it runs in the terminal session
(e.g. "Compact" with a tooltip "writes HANDOFF.md + runs /compact in this
session"), and reflect that the write/compact happens in the pty (the user will see
`/handoff` run there). Pairs with the observer-effect note — this is an explicit,
user-initiated inject, so the cost is acceptable (unlike the auto `/context`).

### Rough story breakdown (to refine in the PRD)
1. **Conditional action bar component** in the HUD tab (Context first) — bottom
   bar, `Cancel` + `Compact`, shown on `ctxPct >= threshold`, dismissible with a
   "don't reshow until higher" rule.
2. **`Compact` action** — inject `/handoff` (then optional `/compact`) via the
   existing keystroke-injection path; disable when no live pty is correlated.
3. **Visual verify** light + dark via `automate-browser`: bar appears past the
   threshold, `Cancel` hides it, `Compact` injects `/handoff` into the correlated
   pty (HANDOFF.md is written by the session), disabled with no live pty.

## Settings feature — surface Claude Code's config in Conan (top-level)
Bring Claude Code's settings (the `/config` screen — Auto-compact, Show tips,
Thinking mode, Fast mode, Default permission mode, Theme, Auto-update channel, …)
into Conan as a **top-level Settings surface** (native **Conan ▸ Settings**, `⌘,`,
opening a Settings view/modal). Note: Conan had a big Settings page in the
dashboard era that was trimmed away in the v4.1/v4.2 Tauri cleanup — this
reintroduces one, but now as a **mirror of Claude Code's own config**, not Conan's.

**Scope reality — read first, edit later (read is safe; edit is a separate, risky
phase). Recommend phasing this; it may be more than one story.**

**Reading the settings — two routes:**
1. **From disk (structured, preferred for editing later).** Claude Code stores
   config across `~/.claude/settings.json` and the global `~/.claude.json`
   (+ project `.claude/settings.json`). Read + display known keys. *Unknown to
   research:* the `/config` screen aggregates more than raw `settings.json`, and
   the exact **row → file → key mapping** (e.g. "Auto-compact", "Thinking mode",
   "Fast mode (Opus 4.7)") is non-obvious and version-dependent. Map carefully;
   don't guess silently.
2. **From a pty capture (consistent with US-009/010).** Capture the `/config`
   frame from the correlated live pty and render the rendered key/value list
   verbatim — same infra as the `/context` and `/usage` captures, no schema
   guessing, always matches what Claude shows. *Cons:* read-only (a captured frame
   can't be written back) and it carries the **same observer-effect inject cost**
   we flagged for `/context` (see the adaptive-refresh + "settled" sections) — so
   capture on demand, not on a timer. The `/config` screen also has tabs
   (Settings / Status / Config / Usage / Stats); Usage/Stats overlap the existing
   Usage widget — scope this to the Settings/Config tabs.

**Editing (later phase — flag the risk):** writing to the config files is the only
non-fragile way to change a setting (driving the `/config` TUI via keystroke
injection is brittle). Open questions to resolve before attempting writes: which
file owns each key; whether a **running `claude` picks up external edits or needs a
restart** (likely restart for many → Conan would have to say so); and write-safety
(don't clobber a hand-maintained `settings.json`; preserve formatting/unknown keys).

**Recommendation:** ship a **read-only Settings mirror first** (disk-read for
structure, falling back to / cross-checked against a captured `/config` frame),
clearly labeled as reflecting Claude's config; defer editing to a follow-up once the
key-mapping + reload behavior is known. Honest UI: show source + "managed by Claude
Code" until edit lands.

### Rough story breakdown (to refine in the PRD)
1. **Research the mapping** — enumerate `/config` rows → config file + key, and
   test whether a running `claude` respects external edits (informs read-only vs
   editable). Short findings note.
2. **Backend read** — `GET /api/claude/config` returning the known settings
   (disk-read, optionally reconciled with a captured `/config` frame).
3. **Settings UI** — top-level view/modal (Conan ▸ Settings, `⌘,`), grouped list,
   search box like Claude's screen, read-only values + source label.
4. **(Later) Editable subset** — only keys with a confirmed safe write path + clear

5. **Visual verify** light + dark via `automate-browser`.

## Theme submenu in the View menu — and the two-layer reality
Surface a **View ▸ Theme** submenu (radio items with a checkmark on the active one,
like Claude Code's own `/theme` picker) instead of the single "Dark Mode/Light Mode"
toggle that's there now (`appMenu.ts:80-91`).

**Critical distinction — there are two independent theme layers:**
1. **Claude Code's `/theme`** (Auto / Dark / Light / colorblind / ANSI / custom) —
   recolors only the **text Claude renders inside the terminal pty**. It's Claude
   Code's own setting (stored in Claude's config); it does **not** affect Conan's
   HUD, chrome, charts, or the terminal *background*.
2. **Conan's app theme** (`ui/src/hooks/useTheme.ts`, light/dark via the `.dark`
   class on `<html>`) — themes the HUD, chrome, charts **and** the terminal's
   bg/fg, because xterm derives from the same tokens (`lib/terminalTheme.ts`,
   `getTerminalTheme()`).

**So "does it trickle to the HUD?" — only Conan's app theme trickles.** Claude's
`/theme` alone never reaches the HUD. The design fork is what the submenu drives:

- **(Recommended) Drive Conan's app theme.** The submenu changes `useTheme`'s
  theme; this already cascades to HUD + chrome + charts + terminal bg/fg. To go
  beyond today's light/dark, extend `useTheme` (and the `index.css` `@theme`/`.dark`
  token sets) with the extra options we want (e.g. an "Auto — match system" via
  `prefers-color-scheme`). This is the layer that gives a unified look.
- **(Optional add-on) Mirror the choice into Claude's terminal `/theme`** so the
  in-terminal text harmonizes with the app theme. Mechanism options: inject
  `/theme` + arrow/enter via the existing keystroke-injection path (fragile TUI
  automation), or write Claude Code's config theme key (may only apply on next
  launch). Research which is reliable before committing; keep it a separate,
  clearly-labeled menu group ("Terminal text theme") so the two layers aren't
  conflated.
- **(Not recommended) Expose only Claude's `/theme`** — it wouldn't touch the HUD,
