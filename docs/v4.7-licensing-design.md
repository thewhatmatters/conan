# Conan v4.7 — licensing design

Pre-spec design for the **license lifecycle** — what shape a license takes, how
it's issued, delivered, activated, verified, revoked, and how all of that
behaves across multi-machine / reinstall / refund. This doc is the
research/decisions floor a future freemium loop builds on.

The hard design constraint that drives every choice: **the Conan app is
offline-by-default.** No phone-home, no analytics ping, no telemetry. License
verification has to work on a Mac in airplane mode. Issuance lives outside the
app; verification lives inside.

---

## The lifecycle in one picture

```
  ┌─ User clicks "Buy Premium" in Settings ▸ License (US-106)
  │   →  opens https://buy.polar.sh/<product-slug> in browser
  │
  ▼
  Polar.sh hosted checkout — collects email + payment, handles VAT/GST
  globally as Merchant of Record. You see net deposits, not tax filings.
  │
  │   on order.created webhook →
  ▼
  conan-license/api/polar-webhook (Vercel, out-of-repo)
  │   1. verifies Polar webhook signature
  │   2. signs an Ed25519 JWT (claims below)
  │   3. records in Polar order metadata `license_id`
  │   4. POSTs the JWT back to Polar via the order metadata API
  │      (or returns it in the webhook response as custom_data)
  │
  ▼
  Polar's receipt email — automatically delivered to customer, includes
  the JWT via {{order.metadata.license}} template var + paste instructions
  │
  ▼
  User → Settings ▸ License → paste JWT → Apply
  │
  ▼
  ui/src/lib/license.ts — verifies signature + exp offline against
                          bundled Ed25519 public key
  │
  ▼
  Writes to ~/Library/Application Support/so.whatmatters.conan/license.jwt
  │
  ▼
  useTier() module store flips to 'premium' →
  every gated surface (Timeline, Pulse, Skills, MCP) reads the new tier
  on next render. No app restart.
```

The two halves — issuance (cloud) and verification (local) — never talk to
each other after the email lands. That's the whole point.

**Why Polar (decided 2026-05-29):** Merchant of Record so we don't owe global
VAT/GST. ~4% + $0.40 per transaction (vs Lemon Squeezy 5% + $0.50, vs Stripe
2.9% + manual tax compliance). Open-source checkout SDK, developer-tool-first
positioning, cleaner webhook + JWT issuance pattern than the alternatives.
Polar absorbs chargebacks. Their hosted checkout + auto-receipt email saves
us a transactional-email vendor entirely (no Resend/Postmark needed for v0).

## 1 · Token format

A standard JWT (`alg: EdDSA`, `typ: JWT`), signed by an Ed25519 private key
held only in the Vercel issuer. The **public key is bundled in the Conan UI
build** as a base64 constant; verification is local, deterministic, fast.

### Claims

```json
{
  "iss": "conan.sh",
  "sub": "lic_01HXXY3F7K2A...",     // unique license id (KSUID-like)
  "email": "randy@whatmatters.so",  // for support lookup + revocation
  "tier": "premium",                // 'premium' (no 'trial' tier — see §5)
  "iat": 1717977600,                // issued-at unix
  "exp": 5083564800,                // paranoia floor only — see note
  "edition": "v1",                  // semver-major; THIS is what gates major upgrades
  "polarOrderId": "01HXXY..."       // Polar order id, for refund correlation
}
```

**Notes on each claim:**
- `sub` (license id) is the **stable identifier**. If a user emails support
  asking for a re-issue or refund, you look this up in Polar order metadata.
- `email` is **not used for verification** (would force phone-home to verify
  ownership). It's there for the user to recognize "yes, that's mine" when
  they paste it, and for support workflows. Not displayed in the UI by
  default — Settings shows last 8 chars of `sub` as a fingerprint instead.
- `tier` is a forward-compatible enum. Today: `premium`. Future: `team`,
  `enterprise`.
- `exp` is a **paranoia floor, not a renewal clock**. Set to ~100 years out
  (e.g. 2130-01-01). The license is one-time, lifetime-of-current-major; the
  real upgrade gate is `edition` (below). `exp` exists so a leaked private
  key with no clock-bounded tokens isn't a forever liability — a key rotation
  + bundled snapshot refresh can still wind down a compromised token set
  before exp. **No clock skew tolerance** — if the user's system clock is
  wildly wrong (off by >1 day) the license refuses to verify; document this
  as a deliberate anti-cheat measure.
- `edition` is the **major-version upgrade gate** (the lifetime-of-current-major
  contract). A `v1` license unlocks every 1.x build forever. The 2.0 release
  is a paid upgrade — its verifier accepts `v2` (and may or may not accept
  `v1`, your choice at the time). Today the 1.x verifier accepts
  `edition: "v1"`; every 1.x build keeps that promise.

### What's deliberately NOT in the claims

- **No machine fingerprint** (no MAC address, no hostname, no hardware ID).
  The license is bound to the customer, not the device. Multi-machine use is
  legitimate (see §6).
- **No `aud` (audience) claim** restricting which build/version can verify it.
  A 2026 license should still verify against a 2028 Conan build (assuming
  the same public key — see §10 for rotation).
- **No usage quotas in the JWT itself.** Quotas are a backend concept; the
  JWT carries entitlement, not metering.

### Signature

`Ed25519` (RFC 8032). Compact, fast to verify (~0.1ms on Apple Silicon),
no key-strength legacy. Library: [`@noble/ed25519`](https://github.com/paulmillr/noble-ed25519)
in the UI (MIT, ~10kB gzipped, zero deps), and `crypto.sign('ed25519', ...)`
in the Node-side issuer (no extra deps).

### Token size

A typical signed JWT comes out at ~280 bytes base64-encoded. Fits in one email
line, no UTF-8 hazards, paste-friendly.

## 2 · Issuance pipeline (Polar.sh)

A separate small repo `conan-license/` (NOT in the Conan main repo — keeps
the private key blast radius small). Massively simpler than a Stripe-based
flow because Polar handles checkout, tax, receipt email, and chargebacks
out-of-the-box.

```
conan-license/
├── api/
│   ├── polar-webhook.ts      ← Polar webhook handler (signs + returns JWT)
│   ├── issue.ts              ← internal admin: re-issue a token by license_id
│   └── revoke.ts             ← internal admin: add a sub to the revocation list
├── lib/
│   ├── sign.ts               ← Ed25519 signing with env-held private key
│   └── polar.ts              ← Polar SDK + signature verification
├── vercel.json
└── README.md
```

**What we DON'T need (vs Stripe-based design):**
- ❌ Resend / Postmark — Polar sends the receipt + license email itself.
- ❌ Domain DKIM/SPF setup for a transactional sender — Polar's domain.
- ❌ Email template testing across clients — Polar's tested template.
- ❌ Refund webhook handler — Polar's customer portal handles it.
- ❌ Chargeback risk + handling — Polar absorbs.

### Webhook flow (`api/polar-webhook.ts`)

1. Receive POST from Polar (`order.created` event).
2. Verify the `Polar-Webhook-Signature` header against `POLAR_WEBHOOK_SECRET`.
   Reject on mismatch (returns 401, Polar will retry).
3. Idempotency: check if the Polar order id has already been issued (Vercel
   KV key `order:<polar-order-id>`). If yes, return 200 — Polar retries are
   expected.
4. Generate `sub` (KSUID), compute `iat`/`exp` (now + 365 days).
5. Sign the JWT with `LICENSE_PRIVATE_KEY_PEM` (env var).
6. Update the Polar order's metadata via their API:
   `PATCH /v1/orders/<id> { metadata: { license: <jwt> } }`.
   This makes the JWT available to Polar's receipt email template variable
   `{{order.metadata.license}}` — Polar sends the email automatically.
7. Store the issuance in KV: `lic:{sub} → {email, polarOrderId, issuedAt}`.
   This is the support lookup table — never read by Conan, only by you and
   the re-issue endpoint.
8. Return 200 to Polar.

**Total handler: ~50 lines.** Compare to the Stripe + Resend equivalent which
was ~150 lines and three external services.

### Polar email template

In Polar's dashboard, customize the post-purchase email template:

```
Subject: Your Conan Premium license

Thanks for buying Conan Premium! Here's your license:

{{order.metadata.license}}

To activate:
1. Open Conan.
2. ⌘, → Settings → License tab.
3. Paste the token above, click Apply.

That's it. Your license expires {{ order.metadata.expires_at | date }} (1
year from purchase) and unlocks every Premium feature on this machine and
any others you install Conan on.

Questions? Reply to this email — it goes to a human.
```

Polar handles delivery, DKIM, format-across-clients, the works.

### Re-issue (`api/issue.ts`) — admin-only

A protected endpoint (`x-admin-key` header) for the support workflow when a
user emails saying "I lost my license." Looks up the `sub` by email (via
Polar customer search) or by `sub` directly, regenerates a JWT with the same
claims (preserving `iat`, optionally extending `exp`), and either:
- Updates the Polar order metadata + tells Polar to re-send the receipt, OR
- Returns the JWT inline for you to paste into a manual email reply.

### Revocation (`api/revoke.ts`) — admin-only

Adds a `sub` to a revocation list (Vercel KV set). The revocation list is
published statically at `https://conan.sh/revoked.json`
(see §7). Triggered when:
- Polar fires an `order.refunded` event → automatic revoke webhook handler.
- You manually invalidate a leaked/shared license (rare).

### Environment variables (Vercel)

| Var | What |
|---|---|
| `POLAR_API_KEY` | Polar API key for the order metadata update call |
| `POLAR_WEBHOOK_SECRET` | Polar webhook signing secret |
| `LICENSE_PRIVATE_KEY_PEM` | Ed25519 private key, PEM-encoded |
| `KV_REST_API_URL` + `KV_REST_API_TOKEN` | Vercel KV for idempotency + revocation list |
| `ADMIN_API_KEY` | Long random string protecting the re-issue/revoke endpoints |

Notably **no email-sender API key needed** — Polar handles it.

**The private key NEVER touches the Conan repo.** Generate it once locally
(`openssl genpkey -algorithm ed25519`), upload to Vercel env, save a backup
in 1Password. The corresponding public key is computed from it
(`openssl pkey -pubout`) and base64-bundled into the Conan UI build.

## 3 · Email delivery (handled by Polar)

**No transactional-email vendor needed.** Polar sends the receipt + license
email automatically from their own infrastructure. Template lives in Polar's
dashboard (§2 covers the contents). DKIM, SPF, deliverability, format-across-
clients are all Polar's problem.

### What we configure in Polar's dashboard

- **Sender name:** `Conan, by What Matters`
- **Reply-to:** `support@whatmatters.so` (a real inbox that gets checked)
- **Template body:** the one in §2 — paste-friendly, plain-text-first, honest
  about multi-machine use, explicit about expiry date.

### Honest UX choices that still apply

- **Long single line** is the token — discourages mid-string line breaks
  that some email clients add. Polar uses their tested template; no client
  audit needed.
- **Multi-machine wording** is explicit ("any others you install Conan on").
- **No "click here" link** that opens Conan via a custom protocol — too
  fragile across email clients, and a paste flow is robust everywhere.
- **Reply-to is a real inbox** — support email lookups need an actual person.

### Future polish (post v0)
- A `conan://license?token=...` deeplink that Polar's template could embed
  as a "1-click activate" button, validated by the Tauri main process. Defer
  until someone actually asks for it; pasting is fine.

## 4 · Activation (the Settings ▸ License paste path)

The UI side is the most visible piece. Implemented as part of US-106.

### The flow

```
SettingsView ▸ License tab
├─ Current tier banner: Free | Trial · 9 days left | Premium · exp 2027-05-29
├─ License field [____________________________] [Apply]
│   on Apply:
│     1. Strip whitespace from pasted text (emails often add leading spaces)
│     2. Call verifyLicense(token) → returns ok | { error: string }
│     3. If ok: write to ~/Library/Application Support/.../license.jwt
│        useTier() store reloads → tier flips immediately, no restart
│     4. If error: inline message below field, field stays populated
│        so the user can edit (don't clear on error — frustrating)
├─ "Buy Premium" button → opens external URL
└─ "What's included" / "What stays free" copy
```

### Verification (in `verifyLicense`)

The local check that runs at activation time and at every app boot:

1. Parse JWT structure — three base64url-encoded parts. Malformed → error
   `"Not a valid license format"`.
2. Verify the signature against the bundled Ed25519 public key. Wrong → error
   `"Invalid license · signature does not match"`. **Most important check** —
   a forged token can't pass this without the private key.
3. Check `iss === "conan.sh"`. Wrong → error
   `"Invalid license · wrong issuer"`.
4. Check `exp > now`. Expired → error `"License expired YYYY-MM-DD"`. (The
   error includes the expiry so users know what to renew.)
5. Check `edition` is one this build understands. Unknown → error
   `"License for a future version of Conan — please update the app"`.
6. Check `sub` against the bundled revocation snapshot (§7). Revoked → error
   `"Invalid license · revoked"`.

All six checks happen offline in <1ms. No network involved.

### Storage

`~/Library/Application Support/so.whatmatters.conan/license.jwt` — same data
dir used for `auth-token` + `active-cwd` (v4.6 hotfix). Plain text, one line,
the JWT. Rationale:

- **Survives app reinstall** (the data dir persists).
- **Cross-machine is just file copy** (legitimate use case — see §6).
- **Easy to delete** by users who want to revert to Free.
- **Not Keychain** — Keychain is for secrets the user shouldn't see; the JWT
  is the user's possession, not a secret from them. Plain file matches the
  mental model.

### What the user sees while typing

The token paste field uses `<input type="password">`-equivalent
masking-by-default with a "show" toggle. Not because the token is a secret
worth hiding (it's the user's own license), but because a 280-character base64
string looks like noise and masking is friendlier when pasting.

## 5 · Trial — there isn't one

**Decided 2026-05-29: no free trial.** The Free tier (see §12) is the trial.
Users can run Conan against their own claude sessions, watch the live
terminal, read the Context and Usage tabs, and see basic Timeline activity
(prompts, tool calls, session lifecycle), indefinitely. If they want
**depth of insight** — skill scoring, plan rows, token analytics, longer
Pulse windows, MCP auth watchdog — they buy.

This is the cleanest possible model. No `trial-start` file. No 14-day clock.
No "Trial · 9 days left" banner state. No soft anti-cheat to outguess. No
abuse vector (delete-data-dir-to-restart). The `tier` JWT claim drops down to
a single value: `premium`.

The framing: **"Conan is free. Premium tells you why — for $39."**

## 6 · Multi-machine

A single license unlocks Premium on any machine the customer installs Conan
on. They literally copy the JWT to each Mac (or paste from email each time).

### Why allow this

- Conan is local — no cloud account model justifies a per-device limit.
- Users have laptop + desktop + Mac Mini setups (the user's own use case);
  per-device licensing would create immediate friction in their core workflow.
- Enforcement of per-device limits requires phone-home, which violates the
  offline-by-default constraint.

### What about abuse?

A user could share their license with friends. In practice:
- Most dev-tool buyers don't share licenses (Sublime Text, Tower, Fork all
  ship this model).
- If you see public sharing of a `sub` (someone pastes it on Reddit),
  revoke it. The revocation list (§7) is the answer.

### The trust-by-design choice

This is a deliberate "trust the customer" model. If conversion suffers because
people share, you change the model — but you don't pre-emptively cripple the
honest majority for the dishonest few.

## 7 · Revocation

Revocation is the **only** part of the lifecycle that needs a network call,
and we keep it carefully optional.

### The mechanism

- The Conan UI build ships with a **revocation snapshot** baked in at build
  time (`ui/src/lib/revoked.ts` — an array of revoked `sub`s as of that
  build's date).
- At runtime, if the app has internet, it tries to refresh the snapshot from
  `https://conan.sh/revoked.json` (a static CDN file generated
  from the KV revocation list every X minutes).
- The refresh is **best-effort**: failure to fetch is silent (offline-by-default
  constraint). The user-cached revocation list lives at
  `~/Library/Application Support/so.whatmatters.conan/revoked.json` and is
  used until the next successful refresh.

### What this means in practice

- A revoked license **continues to work** on an offline Mac until the next
  online launch.
- A revoked license **stops working** the next time the app fetches the
  revocation list.
- A revocation rolled out today reaches all online users within their next
  app session.

### Why this is acceptable

- The most common revocation reason is chargeback / fraud — a few hours of
  continued use isn't materially worse than the loss already taken.
- The alternative (mandatory phone-home for every verification) breaks
  airplane-mode use, which is on-brand-bad for a dev tool.

### Implementation note

The fetch is the **only** outbound call the app makes for licensing. It's
also the only one that touches user IP — if you want to be really clean,
route it through a Vercel function that strips logs (the static file already
does this since static files don't generate per-IP analytics by default).

## 8 · Refunds + re-issues (the human ops)

These happen in the cloud, not the app — but they shape the support story.

### Refund

- User requests refund via reply email.
- You refund in Stripe (or set up auto-refund within 7 days as a policy).
- Stripe fires `charge.refunded` → webhook → `api/revoke.ts` adds the `sub`
  to the revocation list.
- User's app sees the revocation on next online launch, banner reads
  `License revoked · contact support`.

### Re-issue (lost email, lost license file)

- User emails support: "I bought Premium, can't find my license."
- You hit `api/issue.ts?sub=...` (or by email) from your terminal.
- New email goes out with the same token (or a fresh one with the same
  `sub` if the original was lost).

### Multi-purchase (oops, bought twice)

- Refund one, keep the other.
- Both `sub`s are valid until refunded; not a problem.

### These don't need code in Conan

This is all out-of-loop. But the Settings ▸ License "What's included" section
should mention something like "Need help with your license? Email
support@whatmatters.so" so users know there's a human at the other end.

## 9 · The bundled revocation snapshot — backwards-compatibility risk

A subtle but real concern: when a new Conan build ships with a baked-in
revocation list, that list is the *floor* for offline use. If an old version
of Conan is running offline forever, it never sees newer revocations.

### Mitigation

- The baked-in snapshot is regenerated **every build**, so the "floor" is
  always within a release-cycle of current.
- Document in the Conan readme: "If you've been offline for >90 days, your
  license verification reflects revocations as of your last app update."
- Future improvement: a separate `revoked-snapshot.json` file in the .app's
  Resources that can be updated independently of the UI build, so a CI cron
  can refresh just that file. Defer until needed.

## 10 · Key management + rotation

The private key is the **whole game**. If it leaks, anyone can mint Premium
tokens. Treat it like the keys to the kingdom (because it is).

### Where it lives

- **Vercel env var** (encrypted at rest by Vercel).
- **1Password backup** (encrypted, with the family/team vault for redundancy).
- **Nowhere else.** Not on a laptop, not in a repo, not in a Slack DM.

### Generation

```bash
openssl genpkey -algorithm ed25519 -out conan-license-private.pem
openssl pkey -in conan-license-private.pem -pubout -out conan-license-public.pem
# Public key → base64 for embedding in ui/src/lib/license.ts
openssl pkey -in conan-license-public.pem -pubout -outform DER | base64
```

Do this **once**, offline, on a clean machine. Move the private key to
Vercel + 1Password immediately. Delete the local `.pem` file. Never check
either into git.

### Rotation (what if the key leaks)

This is the disaster scenario. The plan:

1. Generate a new keypair (same way, fresh).
2. Ship a Conan release that bundles **both** the old and new public keys —
   verifier tries both. This buys all existing customers a grace period.
3. Re-issue tokens to all existing customers under the new key (they get an
   email with a new token, paste it, done).
4. After 6 months (or some grace window), ship a Conan release that drops
   the old public key. Anyone still using the old token has to re-paste.

This is painful but tractable. The two-key verifier pattern (§step 2) means
no customer is broken on day one.

### Compromise indicators

- A `sub` you never issued shows up in support emails as "my license" (means
  someone's minting tokens).
- The Vercel env reveals an unexpected access pattern.

If either happens: rotate immediately.

## 12 · The gating model — depth of **insight**, not depth of **history**

**Decided 2026-05-30** (revising the original "7d Timeline / 1h Pulse history
cap" model). Why the revision: history-depth gating fails the willingness-to-
pay test for a live tool. Nobody opens Conan at 2pm to scroll back to last
Tuesday's session. The 7-day → 90-day cap never bites the user, so they
never feel the squeeze that drives upgrade. Free becomes "full product
forever" → conversion flatlines.

The right axis is **insight**: free gives users live visibility ("what is
Claude doing right now"); Premium gives them understanding ("**why**, and
how much"). This bites every active session, because the insight rows are
the ones experienced users actually want to read, and it never breaks the
core promise.

### Free vs Premium, surface by surface

**Timeline** — the highest-leverage gate.

| Free | Premium |
|---|---|
| Latest **50 rows** per session | Unlimited rows |
| `PROMPT` rows (full user prompt) | + `SKILL?` rows with BM25 scoring breakdown |
| `PRETOOL` / `POSTTOOL` (name + 1-line snippet) | + Click-to-expand POSTTOOL payloads (full tool input/output) |
| `STOP` (label only — no `+Nk` token chip) | + Token chips on STOP rows |
| `SESSION` start/end | + `PLAN` rows (TodoWrite / ExitPlanMode) |
| `Hooks` filter chip | + `LOOP` rows (Claude `/loop` skill activity) |
|   | + `BUILD` rows (`run-tasks.sh` trail) |
|   | + Filter chips for Plan / Loop / Build |

Free users see Conan working — they see their prompts, the tool calls,
the session lifecycle. Premium users see **why** (skill scoring, plan
intent), **how much** (token chips), and **what changed** (full payloads).

**Pulse** — keep the original range gate, because **the range itself is
the value** (24h Pulse answers "am I going to hit my rate limit before
5pm" — actionable, not nostalgia).

| Free | Premium |
|---|---|
| 15m, 1h ranges | + 6h, 24h ranges |
| All-categories stack | (same) |
| Hover tooltips, legend | (same) |

**Skills** — gate the depth-of-knowledge.

| Free | Premium |
|---|---|
| List of installed skills + descriptions | + `last fired` timestamps |
| Source badge (User / System / Plugin) | + Full transcript-derived firing history |

**MCP** — gate the auth watchdog (a Premium feature that **works while you
work**).

| Free | Premium |
|---|---|
| List of configured servers + live health via `claude mcp list` | + Background OAuth-token watchdog |
| Manual refresh | + Native banner when a token expires |
|   | + One-click reconnect from the banner |

### What stays universally unlocked

- **Live terminal pane** (the whole `xterm.js` surface — this is the entire
  product's primary value, never gated).
- **Context tab** (the live `/context` capture + ProgressCircle).
- **Usage tab** (the live `/usage` Session block + windows).
- **Claude Radio**.
- **Settings + Theme picker + Status mirror**.
- **Native notifications** for `Notification` hook events.
- **Multi-terminal tab strip** + per-tab Timeline split toggle.

The Free tier is **a complete, useful Claude Code observer**. Premium adds
**a layer of analytical depth** on top.

   The overlay stays anchored in the viewport as the user scrolls into
   the blurred zone (so they can't scroll past it to peek at the
   un-overlayed blur). Clicking **Upgrade** opens Settings ▸ License,
   funneling into the existing Buy Premium button. New events arriving
   at the top stay fully visible — the blur is rear-view only.
2. **Per-row "lock" affordances on Premium-only event kinds.** In the
   visible 50 rows, a free user sees a single subtle "Skills considered
   (N)" row instead of N individual `SKILL?` rows, with a small
   `[ Premium ]` chip. Same pattern for `PLAN` / `LOOP` / `BUILD` rows
   and the `+Nk` token chips on `STOP` rows. Click → Settings ▸ License.

Both gates reinforce each other: free users see Conan working in real
time (live PROMPT + tool calls + STOP + SESSION), discover Premium
event types as `[ Premium ]` summary chips in their visible 50, then
hit the blurred-with-lock-overlay at row 50 when they try to scroll
back. Three distinct upgrade moments per session, none of them hostile.

### Why this beats the old history-depth model

| Axis | Old (history depth) | New (insight depth) |
|---|---|---|
| Bites a free user with one active session? | No — 50 events fit in 7 days easily | Yes — they hit the 50-row cap mid-session |
| Touches the live experience? | No (history only) | Yes (intentionally — but only the "advanced" rows) |
| Feels like a real product? | "More history" — weak | "See why and how much" — concrete |
| Sells on the marketing page? | "90d vs 7d" — meh | "Skill scoring + tool payloads + plan tracking" — clear |
| Risks breaking the core value? | None | Low — basic events stay visible; only depth-of-insight is gated |

## 13 · What the freemium loop changes about Conan's repo

- **Adds:** `ui/src/lib/license.ts`, `ui/src/lib/revoked.ts`,
  `ui/src/hooks/useTier.ts`, `src/license/index.ts` (backend mirror for the
  cap routes), a new `Settings ▸ License` tab, the per-row "lock"
  affordances + end-of-Timeline footer.
- **Touches:** the Timeline filter / render path (gate event types +
  enforce 50-row cap + footer), Pulse range selector (disable 6h / 24h on
  Free), Skills tab (omit `last fired` column on Free), MCP tab (no auth
  watchdog start on Free), the build pipeline (bake the revocation
  snapshot at build time).
- **Doesn't touch:** the live terminal, Context tab, Usage tab, Radio, or
  Settings.

This doc is the technical-decisions floor (how + why) — the product backlog
(what + why) lives in whatever loop pulls these decisions into stories.

## 14 · What lives in the separate `conan-license/` repo

A non-exhaustive design checklist for the issuer-side repo. With Polar as
MoR, this is ~half the work of the original Stripe + Resend plan
(estimated effort: ~3 hours to ship v0):

- [ ] Polar.sh account + Conan Premium product configured ($39/yr).
- [ ] Polar's hosted checkout URL noted (used by US-106 Buy button).
- [ ] Polar receipt email template customized (the one in §2/§3).
- [ ] Vercel project linked to a clean GitHub repo.
- [ ] Ed25519 keypair generated locally, private key in Vercel env +
      1Password, public key handed to Conan UI.
- [ ] `api/polar-webhook.ts` — Polar `order.created` → JWT → write back to
      Polar order metadata. Idempotent on Polar order id.
- [ ] `api/issue.ts` (admin-only re-issue) + `api/revoke.ts` (admin-only).
- [ ] `api/polar-refund-webhook.ts` — Polar `order.refunded` → auto-revoke.
- [ ] Vercel KV configured for idempotency + revocation list.
- [ ] Static `public/revoked.json` regenerated by a cron from the KV list.
- [ ] A bash one-liner / Makefile for the admin operations (revoke, re-issue,
      lookup by email).
- [ ] README documenting the environment + the disaster-recovery (key
      rotation) procedure.

**Removed from the v0 checklist (vs Stripe-based design):**
- ~~Stripe webhook secret + signature verification~~ — Polar's simpler
- ~~Resend/Postmark domain DKIM+SPF setup~~ — Polar's domain
- ~~Email template testing across clients~~ — Polar's tested template
- ~~Stripe Checkout page configuration~~ — Polar's hosted checkout
