## Context tab — user-facing "Auto" context-tracking toggle (inline with manual refresh)
Add a **toggle on the Context tab** that lets the user turn **"Auto" context
tracking on or off**:
- **Auto ON** — Conan auto-injects `/context` to keep the Context widget fresh
  (the adaptive, observer-effect-aware cadence from v4.3, not every turn).
- **Auto OFF** — no auto-injects; the user keeps the existing **on-demand
  `↻ /context` refresh button** to update the widget when they choose.

**Layout ask:** the toggle and the refresh button sit **side-by-side / inline**
in the Context tab header — one control group, the toggle gating whether the
auto path runs and the button always available as the manual path.

**This is surfacing an existing capability, not new machinery.** v4.3 already has
the auto-refresh path and its off-switch — they're just not user-facing in the
HUD yet:
- The auto path is `autoRefreshContextOnStop` (adaptive trigger off the event
  stream) in `src/terminal/index.ts`, fired from the `Stop` branch in
  `src/gateway/index.ts`, gated by the `CONAN_CONTEXT_AUTOREFRESH` env var.
- The manual path is the `↻ /context` button in the Context widget
  (`ui/src/components/Widgets.tsx`), hitting
  `POST /api/claude/sessions/:id/context/refresh`.
- Passive capture (parse only when the user runs `/context` themselves) stays the
  always-cheap path underneath both.

v4.4 lifts the env gate into a **per-user (or per-session) UI setting** the toggle
drives, so the user controls the observer-effect tradeoff directly instead of via
an env var.

**Honest UI (carry the v4.3 observer-effect framing):** the toggle's label/tooltip
should make clear that Auto **spends context to measure context** (each inject is
~4–6k tokens in a normally-loaded session), so leaving it off + refreshing
on-demand is the cheap default. The "live · from /context" face already signals
that refresh consumes context — keep that consistent.

### Open questions (resolve at PRD time)
- **Scope of the setting:** global (one Conan-wide preference) vs per-session
  (each correlated session remembers its own Auto state)? Default suggestion:
  global, persisted like the theme preference, with the toggle reflecting it.
- **Persistence:** where the toggle state lives (localStorage like `useTheme`, or
  written back so the gateway's `Stop`-branch auto path honors it). The auto path
  runs gateway-side, so the toggle must reach the gateway (not just the UI) — e.g.
  the refresh route / a small settings write — for OFF to actually suppress
  injects, not just hide them.
- **Default:** OFF (cheap, no surprise injects) unless we decide the adaptive
  cadence is cheap enough to default ON.

### Rough story breakdown (to refine in the PRD)
1. **Wire the toggle through to the gateway auto path** — replace the
   `CONAN_CONTEXT_AUTOREFRESH` env-only gate with a setting the UI can flip, read
   by the `Stop` branch (`src/gateway/index.ts`) / `autoRefreshContextOnStop`
   (`src/terminal/index.ts`); keep the env var as an override/floor if useful.
2. **Context-tab toggle + inline refresh button** in `ui/src/components/Widgets.tsx`
   — a toggle (shadcn `Switch`/`Toggle`) placed **side-by-side** with the existing
   `↻ /context` button in the Context header; OFF disables/relabels nothing on the
   button (manual stays available), it only gates the auto path.
3. **Persist the preference** and reflect it on load (localStorage or a small
   settings read), consistent with how the gateway path reads it in story 1.
4. **Honest labeling** — tooltip/subtext noting Auto consumes context per refresh.
5. **Visual verify** light + dark via `automate-browser`: toggle + button render
   inline; ON re-enables adaptive auto-refresh, OFF stops auto-injects while the
   manual button still refreshes on click.

## Settings dialog — surface Claude's real settings, tabbed (Status / Config) + editable
Grow the read-only Settings mirror (US-007/008) into a faithful, **editable** mirror of
Claude Code's own `/settings`, organized by the **same tabs Claude uses — Status and
Config** (see screenshots). **Config** rows become live controls: **toggle switches for
booleans, dropdowns for enumerated values** (e.g. Theme, Default permission mode,
Worktree base ref, Auto-update channel), and text/number inputs where neither fits.
**Status** stays read-only (version, session, cwd, login/org/email, model, MCP servers,
setting sources).

### ⚠️ The lesson from the theme feature applies directly
Writing Claude's config takes effect **next session, not live** — a running `claude`
reads settings at startup and does **not** hot-reload `settings.json`. So this dialog
must be **honest** that edits apply on the next session start (a small "applies next
session" note), or it'll disappoint the same way `/theme` mirroring did. Don't imply
live effect.

### Crux / dominant risk: the settings SCHEMA (key ↔ type ↔ allowed values)
The hard part isn't the controls — it's knowing each setting's **on-disk key, its type
(boolean / enum / number / string), and for enums the allowed values + their labels**,
plus which file/scope owns it. What we have + need:
- **Have:** Conan already curates a key↔label map — `SETTINGS_KEYS` + `GLOBAL_KEYS` in
  `src/config/index.ts` (e.g. `theme`, `autoCompactEnabled`, `alwaysThinkingEnabled`,
  `editorMode`, `autoUpdates`, `model`, …) and reads current values via `readClaudeConfig`.
- **Need:** extend each entry with a **`type` + `options`** (for enums) + default.
  Claude's `/config` shows ~30 settings ("12 more below"); curate the **editable
  subset** we're confident about and leave the rest read-only rather than guessing.
- **Sourcing the schema (be diligent, don't guess):** the enum values are extractable
  from the installed `claude` binary's embedded strings — the **proven approach** we
  used for the theme set (`grep -aoE` over the binary) — cross-checked against Claude's
  docs. Map Claude's friendly labels (screenshot) to the real keys; a wrong key/type
  silently writes garbage, so each editable row needs verification.

### Write-back
- A generic config-write: **read-modify-write preserving every other key** (the exact
  pattern proven in the now-removed `setClaudeTheme`; reuse the technique generically),
  to the correct scope file (User `~/.claude/settings.json` by default).
- New route, e.g. `POST /api/claude/config` `{ key, value }`, validated against the
  schema (only known keys + type-checked values) so the dialog can't write junk.
- Reflect the write outcome honestly (ok / no-config / write-error), like the theme
  write did.

### Status tab (read-only)
Mirror the Status screen: Version, Session name/ID, cwd, Login method, Organization,
Email, Model, MCP servers (`N connected · need auth · disabled · failed`), Setting
sources. Conan already has pieces — the MCP reader (kept in US-004 for the Context
breakdown), the config `files`/scopes from `readClaudeConfig`, and cwd. Source the rest:
version (`claude --version` / the binary), account (org/email/login) from
`~/.claude.json` or the credentials file; session id/name from the correlated session.

### Open questions (resolve at PRD time)
- **Write scope:** User settings only, or also Project (`<cwd>/.claude/settings.json`)?
  Start with **User**; Project editing is a later nicety.
- **Editable subset:** which keys are safe to expose now (the obvious booleans + the few
  known enums) vs. left read-only until their schema is confirmed.
- **Type detection:** curated per-key schema (recommended — explicit, safe) vs. inferring
  type from the current value (fragile for enums/empty).
- **Live-reflect:** since edits apply next session, do we show the on-disk value (what
  the next session will use) and not pretend the running session changed?

### Rough story breakdown (to refine in the PRD)
1. **Schema:** extend `SETTINGS_KEYS`/`GLOBAL_KEYS` with `type` + `options` + `tab`
   (Status/Config); source enum values from the `claude` binary + docs; cover a
   confident editable subset.
2. **Write route + validator:** `POST /api/claude/config` `{key,value}`, read-modify-write
   preserving other keys, validated against the schema; returns the outcome.
3. **Tabbed Settings UI** (`SettingsView.tsx`): Status (read-only) + Config (editable) —
   shadcn `Switch` for booleans, `Select` for enums, inputs otherwise; an "applies next
   session" note; keep the existing search.
4. **Status tab data:** wire version / account / model / MCP / setting-sources / session.
5. **Visual verify** light + dark via `automate-browser`: a toggle flips + persists to
   `settings.json` (other keys preserved), a dropdown writes the exact enum value, and

## Bind session-scoped HUD widgets to the ACTIVE terminal tab (Context/Plan/Skills)
**Bug:** the Context tab (and Plan + Skills — every session-scoped widget) shows the
*wrong* session when more than one terminal tab is open. Opening a new tab still shows
the previous tab's context.

**Root cause (verified):**
- `App.tsx` derives `correlatedSession` by taking **all** terminals' sessions and
  returning `matched.find(s => s.status === "running") ?? matched[0]` — i.e. the first
  running correlated session in iteration order, **not the focused tab's**.
- `App` never learns which tab is active: `activeTid` lives entirely inside
  `TerminalPane` (`useState`, ~line 80) and is never lifted up — so the HUD *can't*
  scope to the focused tab even in principle.

**Fix:** bind the session-scoped widgets to the **active tab's** session.
1. `TerminalPane` exposes the active tab — an `onActiveTidChange(tid)` callback (or lift
   the tab state up), fired on tab switch/open/close and on mount.
2. `App` holds that `activeTid` and derives the active session as
   `terminals.get(activeTid)?.sessionId` → the matching session (via `useTerminals` +
   `useSessions`), replacing the `find(running) ?? matched[0]` heuristic for
   `activeSession`/`widgetSession`.
3. Context / Plan / Skills then follow the focused tab. A brand-new tab whose `claude`
   hasn't correlated yet correctly shows **"no session yet"** (empty) rather than the
   *previous* tab's data — correlation lands a beat later via `/api/terminals`.

**Edge notes:** correlation lag on a fresh tab is expected (show empty, not stale);
keep the existing fallbacks (running → most-recent) only for the **no-tab-correlated**
case, not as the primary binding.

### Rough story breakdown (to refine in the PRD)
1. `TerminalPane`: surface `activeTid` upward (callback prop), covering switch/new/close.
2. `App`: track `activeTid`, derive the active session from it, repoint
   `activeSession`/`widgetSession` (Context/Plan/Skills) + the timeline's
   `visibleSessionId`.
3. Visual verify via `automate-browser`: open a 2nd terminal → Context/Plan/Skills
   re-point to the new tab (empty until it correlates), switch back → they follow.

## Pulse chart — dark-mode axis legibility + tooltip overlap fixes
Two readability bugs on the Pulse `AreaChart` (vendored Tremor), both visible in dark mode:

1. **Axis tick labels are too dark to read.** The X/Y axis ticks render in
   `fill-muted-foreground`, which is too dim against the dark chart background — the time
   labels (e.g. `17:59` / `17:35`) and Y ticks nearly vanish. **Fix:** bump the axis tick
   fill to a more legible token (e.g. `fill-foreground/60–70`, or a dedicated chart-axis
   token) so it reads in both themes. While here, the hover **cursor line is a hard-coded
   `#d1d5db`** (not theme-aware) — switch it to a semantic stroke too.

2. **Hover tooltip overlaps the in-chart legend.** The tooltip floats at the top of the
   plot and collides with the chart's own legend row, so the tooltip's time label (`05:35`)
   visually overlaps the legend text (`Prompts — Session — Tools`) — looks like a
   transparent/garbled background. **Root cause:** the chart renders **two** legends — the
   Tremor in-chart `showLegend` one AND PulseChart's own **footer legend swatches** (with
   per-category totals). They're redundant.
   **Recommended fix:** **drop the in-chart `showLegend`** (keep the richer footer legend) —
   this removes the overlap entirely and declutters the plot. If we want to keep an in-chart
   legend instead, give the tooltip an opaque, higher-`z` container and/or move the legend
   out of the plot (bottom), but dropping the redundant one is simpler.

### Anchors
- `ui/src/components/charts/AreaChart.tsx` — XAxis/YAxis `tick` styling
  (`fill-muted-foreground`, ~`:698`/`:728`); hard-coded cursor `stroke: "#d1d5db"` (~`:751`);
  the default `ChartTooltip` container (`bg-card`/`border-border`, ~`:395`).
- `ui/src/components/PulseChart.tsx` — passes `showLegend` to `<AreaChart>` (~`:151`) while
  also rendering its own footer legend (~`:164-183`); `compact` is the HUD-strip path.

### Rough story breakdown (to refine in the PRD)
1. Bump axis tick fill to a legible token + make the cursor stroke theme-aware in
   `AreaChart.tsx` (shared by any future chart, so keep it token-driven).
2. Drop the redundant in-chart `showLegend` from PulseChart's `<AreaChart>` (footer legend
   stays the source of truth).
3. Visual verify light + dark via `automate-browser`: axis labels clearly readable; hover
   tooltip no longer collides with any legend; footer legend + totals intact.

## Claude Radio — bottom toolbar play/pause for the YouTube live stream
Add a slim **app-wide bottom toolbar** with a **play/pause control** that streams **Claude
Radio** — the YouTube live stream at <https://www.youtube.com/live/YmQ7jRgf4f0> (video id
`YmQ7jRgf4f0`) — directly inside the app. A little ambient-audio affordance while you work.

**Feasibility — yes, and CSP won't block it.** The Tauri webview (WKWebView) can host a
**YouTube IFrame Player** (the sanctioned embed path), and `security.csp` is currently
`null` (permissive) so no `frame-src`/`script-src` allowlisting is needed for v4.4. Play/
pause is driven via the **YouTube IFrame Player API** (`playVideo()`/`pauseVideo()`); the
iframe can be rendered **offscreen / 1×1** so it's audio-only (the toolbar is the UI).

**Autoplay caveat (be honest in the UI):** browsers block **autoplay *with sound*** until a
user gesture, so it can't truly auto-play audio on launch. Two options: (a) **default to
paused**, the user hits Play (the click is the gesture) — simplest/most honest; or (b)
**autoplay muted**, then unmute on the first Play click. Recommend (a). The button is the
single source of truth for state (`playing`/`paused`), reflecting the player's actual state
via the API's `onStateChange`.

**Resilience:** a live stream can end or be offline — handle the player error/unstarted
state gracefully (disable + a muted "Radio offline" label) rather than a dead button.
