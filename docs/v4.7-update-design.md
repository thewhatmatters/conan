# Conan v4.7 — auto-update + notarization design (companion to the freemium loop)

Pre-spec design for the **app update lifecycle** — how a Conan instance learns
about new versions, downloads them, verifies them, and installs them without
the user manually re-downloading a DMG. Pairs with
[`docs/v4.7-licensing-design.md`](./v4.7-licensing-design.md) because updates
and licensing are *coupled by design* (the bundled revocation snapshot in §9
of the licensing doc stays fresh **only** if updates land).

Existing operational floor: [`docs/tauri-desktop.md`](./tauri-desktop.md) §
"Signing & notarization" already documents the Developer ID + notarytool
step for the .app bundle. **This doc adds the auto-update layer on top of
that.** Read both together.

The hard constraint: **updates must not interrupt a running task.** A user
mid-`/loop` or mid-`run-tasks.sh` can't have Conan force-quit on them. Update
checks are passive; install is user-confirmed or deferred to next launch.

---

## 1 · Why auto-update pairs with the freemium loop

Three couplings between updates and licensing:

1. **Revocation freshness.** The bundled `revoked.json` snapshot (licensing
   design §9) is regenerated at every build. A user who installed v0.1 and
   never updated would carry that release date's revocation snapshot
   forever — useless against tokens revoked after their install date. Auto-
   updates keep the floor moving.
2. **`edition` claim in the JWT.** Licenses are versioned via the `edition`
   claim. When `edition` changes (e.g. v0 → v1 with new feature gates), users
   need both the new binary AND a re-issued license to unlock. Auto-update
   delivers the new binary; the email re-issue delivers the new license.
3. **Bug-fix delivery to paying users.** Cannot ship a paid app without an
   update channel — paying users will absolutely report bugs, and the answer
   "redownload the DMG manually" doesn't fly.

Without auto-update, the freemium loop ships a product that decays. With it,
the freemium loop ships a product that compounds.

## 2 · Lifecycle in one picture

```
  ┌─ CI / local build of v4.8
  │   1. tauri build  (Developer-ID signed .app + .dmg)
  │   2. notarize     (xcrun notarytool — Apple verifies)
  │   3. staple       (xcrun stapler staple — embeds the ticket)
  │   4. minisign     (sign the DMG with the update keypair)
  │   5. write manifest latest.json:
  │       { version: "4.8.0", pub_date, signature, url }
  │   6. upload .dmg + latest.json to CDN
  │
  ▼
  https://conan.whatmatters.so/updates/latest.json
                   (Cloudflare R2 or Vercel)
  │
  ▼  app launches (or user clicks "Check for updates")
  │
  tauri-plugin-updater:
    1. fetch latest.json
    2. compare semver
    3. download .dmg (resumable, throttled)
    4. verify minisign signature against bundled public key
    5. surface "Update available — install now / later"
       (no banner during an active task — see §9)
  │
  ▼  user confirms (or deferred to next launch)
  │
  Tauri replaces the .app, relaunches, license file persists.
  Revocation snapshot is now from the new build's date.
```

The signing chains are layered:
- **Apple Developer ID** signs the `.app` — Gatekeeper accepts the install.
- **Apple notarization ticket** is stapled — Gatekeeper accepts launch without
  network.
- **Minisign** signs the `.dmg` — `tauri-plugin-updater` verifies the
  download isn't tampered after it leaves the CDN.

Three different keypairs in total (Apple Dev ID, Apple notary, minisign +
license Ed25519 = 4 if you count licensing). Each has a different scope.

## 3 · `tauri-plugin-updater` (the runtime piece)

[Official Tauri v2 plugin](https://v2.tauri.app/plugin/updater/). Already
written, tested, in-tree at Tauri's repo. We don't write update code — we
configure it and host the manifest.

### Install + configure

```bash
cargo add tauri-plugin-updater   # in src-tauri/Cargo.toml
npm install @tauri-apps/plugin-updater   # in ui/
```

`src-tauri/tauri.conf.json`:

```json
{
  "plugins": {
    "updater": {
      "endpoints": [
        "https://conan.whatmatters.so/updates/{{target}}/{{arch}}/{{current_version}}"
      ],
      "pubkey": "untrusted comment: ...\n<base64 minisign public key>",
      "windows": { "installMode": "passive" }
    }
  }
}
```

`endpoints` resolves the `{{target}}` / `{{arch}}` / `{{current_version}}`
template at runtime → e.g. `…/darwin/aarch64/0.1.0`. That URL serves the
manifest. The server can return a 204 No Content when no update is available,
saving the client a JSON parse.

The `pubkey` is the minisign verifier — bundled into the .app binary at build
time. **This is the second key we have to manage** (the first being the
license Ed25519). Both have the same management model: kept off the repo,
backed up in 1Password.

### Capabilities allowlist

Tauri v2 requires capability declarations for plugin permissions. Add to
`src-tauri/capabilities/default.json`:

```json
{
  "permissions": [
    "updater:default",
    "updater:allow-check",
    "updater:allow-download-and-install"
  ]
}
```

## 4 · Update manifest

The JSON `tauri-plugin-updater` consumes. Shape per Tauri's v2 spec:

```json
{
  "version": "0.2.0",
  "notes": "v0.2 — freemium tier + multi-day pulse + MCP auth watchdog. See full notes at conan.whatmatters.so/changelog#0.2.0",
  "pub_date": "2026-07-15T19:00:00Z",
  "platforms": {
    "darwin-aarch64": {
      "signature": "untrusted comment: ...\n<base64 minisign signature>",
      "url": "https://conan.whatmatters.so/updates/dl/Conan_0.2.0_aarch64.dmg"
    },
    "darwin-x86_64": {
      "signature": "...",
      "url": "https://conan.whatmatters.so/updates/dl/Conan_0.2.0_x86_64.dmg"
    }
  }
}
```

**Notes:**
- `notes` is plain text. Keep it short — Tauri displays it in the update
  prompt; long-form lives at the changelog URL.
- One entry per `{target}-{arch}` combo. macOS Apple Silicon (`darwin-aarch64`)
  is the primary target today; `darwin-x86_64` for Intel Macs is a hedge —
  drop it if/when bundling stops producing x86_64 artifacts.
- The `url` is the direct DMG download. `tauri-plugin-updater` downloads,
  verifies, then runs the installer flow.

## 5 · Hosting

Cheapest and simplest options for serving manifest + DMGs:

| Option | Bandwidth pricing | Setup effort | Verdict |
|---|---|---|---|
| **Cloudflare R2** | $0.015/GB stored, $0 egress | One-time bucket + custom domain | **Recommended** — zero egress fees scales infinitely |
| Vercel | $0.20/GB egress over 100GB free | Already on Vercel for licensing | OK for v0 but DMGs at ~60MB get expensive fast |
| GitHub Releases | Free | Tags + release assets | Works but slow downloads, no custom domain |
| S3 + CloudFront | $0.085/GB egress | Most setup | No reason to pick over R2 |

**Recommendation: Cloudflare R2.** Bucket: `conan-updates`. Custom domain:
`updates.whatmatters.so` or `conan.whatmatters.so/updates/`. R2's zero egress
matters because each Conan user downloads a ~60MB DMG per update — at 10k
users x 4 updates/year = 2.4TB. R2 = effectively free; Vercel = $400+/yr.

### Directory layout on R2

```
/manifest/darwin/aarch64/latest.json    ← the updater's endpoint result
/manifest/darwin/x86_64/latest.json     ← (if we ship Intel)
/dl/Conan_0.2.0_aarch64.dmg             ← signed DMG
/dl/Conan_0.2.0_x86_64.dmg
/dl/Conan_0.1.0_aarch64.dmg             ← keep N old versions for rollback
```

The manifest URL the plugin hits actually goes through a Cloudflare Worker
that:
1. Reads the request's `current_version` template variable.
2. Compares against `latest.json`'s `version`.
3. Returns the manifest if newer is available, 204 if not.
4. Logs nothing PII — just counts (version, target, arch) for release telemetry.

The Worker is ~20 lines, free tier covers it.

## 6 · Signing keys (the four-key picture)

Conan ends up with four separate signing keys at launch. Worth being explicit:

| Key | Type | Purpose | Where it lives | Public side |
|---|---|---|---|---|
| **Apple Developer ID** | RSA 2048 | Signs the .app for Gatekeeper | Mac Keychain (the build machine) | Apple's notary verifies |
| **Apple App-specific password** | Apple ID secondary auth | Notarization API auth | 1Password + env | n/a |
| **Minisign** | Ed25519 | Signs DMG for tauri-updater | Build env (offline laptop ideally) + 1Password backup | Bundled in .app via tauri.conf.json |
| **License Ed25519** | Ed25519 | Signs JWT licenses | Vercel env + 1Password | Bundled in UI build via `ui/src/lib/license.ts` |

The two Ed25519 keypairs are deliberately separate — different lifecycles,
different blast radii. If the minisign key leaks, attackers can push fake
updates to Conan installs. If the license key leaks, attackers can mint fake
Premium tokens. Either is bad; coupling them would make any leak twice as bad.

### Generating the minisign keypair

```bash
brew install minisign
minisign -G -p conan-update-public.key -s conan-update-secret.key
# Public key contents → tauri.conf.json `pubkey`
# Secret key → 1Password (and your build CI env if you automate)
```

Do this once, locally, on a clean machine. Same hygiene as the license key.

## 7 · Build pipeline (the steps from `npm run tauri:build` to a published update)

Today's flow ends at `Conan.app` + `Conan_0.1.0_aarch64.dmg`. The full
"publishable update" flow adds 4 steps after that:

```bash
# 1. Build (existing) — produces ad-hoc signed .app + .dmg
PATH="$HOME/.cargo/bin:$PATH" CI=true npm run tauri:build

# 2. Re-sign with Developer ID + notarize (Tauri does this when env vars set,
#    cross-ref docs/tauri-desktop.md)
export APPLE_SIGNING_IDENTITY="Developer ID Application: Randy <name> (TEAMID)"
export APPLE_ID="randy@whatmatters.so"
export APPLE_PASSWORD="$(op read 'op://Private/Apple App Password/password')"
export APPLE_TEAM_ID="<TEAMID>"
PATH="$HOME/.cargo/bin:$PATH" CI=true npm run tauri:build

# 3. Verify notarization stuck
spctl -a -t exec -vvv src-tauri/target/release/bundle/macos/Conan.app
# → should print: source=Notarized Developer ID

# 4. Sign the DMG with minisign
DMG=src-tauri/target/release/bundle/dmg/Conan_0.2.0_aarch64.dmg
minisign -Sm "$DMG" -s ~/keys/conan-update-secret.key

# 5. Build the manifest
cat > /tmp/latest.json <<EOF
{
  "version": "0.2.0",
  "notes": "v0.2 freemium tier + multi-day pulse + MCP auth watchdog.",
  "pub_date": "$(date -u +%Y-%m-%dT%H:%M:%SZ)",
  "platforms": {
    "darwin-aarch64": {
      "signature": "$(cat $DMG.minisig | base64)",
      "url": "https://updates.whatmatters.so/dl/Conan_0.2.0_aarch64.dmg"
    }
  }
}
EOF

# 6. Upload to R2 (rclone or wrangler)
wrangler r2 object put conan-updates/dl/Conan_0.2.0_aarch64.dmg --file "$DMG"
wrangler r2 object put conan-updates/manifest/darwin/aarch64/latest.json --file /tmp/latest.json
```

This is 5 lines of work after the build — easy to wrap in a `npm run release`
script. Worth doing because at the moment the user has been hand-running
`npm run tauri:build` ~5 times in this session; a single release command is
strictly better.

### CI later (not v0)

When tagged, push runs the above on a GitHub Action. macOS runner ($0.08/min,
~12 min build = $1/release). Defer until the manual flow proves stable —
manual gives you a chance to verify each step.

## 8 · Update UX in the running app

The plugin gives you the mechanism. The **policy** is on us.

### When to check

- **Boot:** check on app launch, async, non-blocking. 95% of the time returns
  "no update" silently.
- **Daily:** if the app stays open for >24h, re-check.
- **Manual:** Help ▸ Check for Updates… menu item (always available).

### When to install

- **Default: deferred to next launch.** Update is downloaded silently in
  background, applies on next quit + relaunch. Zero disruption.
- **User-prompted:** If the update is critical (revocation snapshot urgency,
  security), a small banner appears: "Update to v0.2.1 is ready · Install now
  or wait until next launch." Both are valid choices.
- **Never auto-relaunch.** A user in the middle of a `/loop` task being
  yanked is the worst-case scenario — far worse than a 1-day-stale revocation.

### Status

Tauri's plugin exposes events: `error`, `pending`, `downloading`, `finished`.
The Settings ▸ Updates section (new tab? or under About?) shows current
version, last check time, and a manual check button.

### What about the gateway sidecar?

The sidecar is part of the .app bundle (Contents/Resources/runtime/gateway.cjs
+ node binary). Replacing the .app replaces the sidecar atomically. No
separate update channel needed.

**Caveat:** the running gateway sidecar holds the SQLite DB open. On update
install, Tauri quits the app (which triggers the stdin-EOF watchdog that
terminates the sidecar), copies the new .app over the old, and relaunches.
SQLite WAL flushes on close, so no data loss — but the gateway DB lives at
`~/Library/Application Support/so.whatmatters.conan/conan.db` (outside the
.app), so it survives the update naturally.

## 9 · Update channels (stable vs beta)

Two endpoints, one config flag:

| Channel | URL | Audience |
|---|---|---|
| `stable` | `https://updates.whatmatters.so/manifest/darwin/aarch64/latest.json` | Everyone (default) |
| `beta` | `https://updates.whatmatters.so/manifest-beta/darwin/aarch64/latest.json` | Settings ▸ Updates toggle for power users |

Users on `beta` get pre-release builds. The toggle lives in Settings; flipping
it changes which manifest the plugin reads from. Same minisign verification.

**Why:** lets you dogfood v4.8 with willing testers (the beta program
mentioned in the previous strategic chat) without forcing every paying user
onto an unreleased build.

**Recommended for v0:** ship `stable` only. Add `beta` once you have 10+ real
users and want to test before promoting builds.

## 10 · Failure modes (what breaks, what falls back)

| Failure | Behavior | Acceptable? |
|---|---|---|
| Manifest fetch fails (offline) | Updater silently does nothing | Yes — offline-by-default brand stance |
| Manifest fetch fails (CDN down) | Updater silently does nothing | Yes — temporary, retries next check |
| Manifest parse fails (corrupted) | Logged, no update offered | Yes — surface to logs only, never user |
| DMG download fails mid-stream | Updater retries with exponential backoff; gives up after 3 | Yes |
| Minisign signature mismatch | **Hard fail.** Update rejected, user sees error in Settings ▸ Updates | Yes — this is the attack scenario, never silent |
| Notarization ticket missing on DMG | Gatekeeper refuses launch post-update | **Bad** — covered by pre-release verification step (§7 step 3) |
| Disk full mid-install | Tauri's plugin handles the rollback | Yes — old .app preserved until new is fully written |
| User declines indefinitely | Stays on old version forever | Yes — their right; revocation list goes stale but app still works |

The minisign-mismatch path is the security floor. Even if R2 is somehow
compromised and serves a tampered DMG, the bundled public key in the .app
rejects it. The attacker needs both R2 access AND the minisign secret key.

## 11 · How updates pair with licensing

Three concrete behaviors:

### Bundled revocation snapshot
On every update install, the new build ships with a regenerated `revoked.ts`
constant. Users go from "revocation knowledge as of v0.1 build date" to "as of
v0.2 build date" instantly. This is the cleanest channel for revocation reach.

### `edition` claim migration
A v0 license has `edition: "v0"` in the JWT. If a future Conan introduces
`edition: "v1"` (e.g. team licensing), the verifier in `ui/src/lib/license.ts`
decides:
- v0 license + v0 binary → unlock all v0 features ✓
- v0 license + v1 binary → unlock v0 features (Pulse 7d, Timeline retention,
  Skills history, MCP watchdog), but NOT v1 features (team dashboard). User
  sees "Some features require a v1 license — contact support to upgrade."
- v1 license + v0 binary → unlock all v0 features ✓

Updates carry the new verifier code. Without updates, users would get stuck
on v0-only forever.

### Trial reset prevention
Updates **preserve** the trial sentinel file (`~/Library/Application Support/.../trial-start`).
Updating from v0.1 → v0.2 doesn't restart the trial.

## 12 · CI/CD (defer, but design now)

For v0 the release flow is the bash steps in §7 run manually. When it stops
being fun:

### GitHub Actions setup

```yaml
# .github/workflows/release.yml (sketch)
on:
  push:
    tags: ['v*']

jobs:
  build-macos:
    runs-on: macos-14
    steps:
      - checkout
      - install rust toolchain
      - npm ci
      - import Apple cert (encrypted, GitHub Actions secret)
      - tauri:build (signs + notarizes via env)
      - minisign DMG
      - build manifest JSON
      - upload to R2 via rclone
      - publish GitHub release with .dmg + changelog
```

GitHub Actions secrets needed:
- `APPLE_CERTIFICATE_P12` (base64-encoded)
- `APPLE_CERTIFICATE_PASSWORD`
- `APPLE_ID`, `APPLE_PASSWORD`, `APPLE_TEAM_ID`
- `MINISIGN_SECRET_KEY` (base64)
- `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`

All set once via `gh secret set …`. Cost: ~$1 per release on the macOS runner.

### Bypass for v0

For v0 just script the bash flow as `scripts/release.mjs`. Less moving parts,
fully reproducible, you watch each step. Move to CI once releases happen
weekly+.

## 13 · Open decisions

| Decision | Default proposed | Notes |
|---|---|---|
| Update endpoint host | `updates.whatmatters.so` on R2 | vs `conan.whatmatters.so/updates/` — second is simpler DNS but conflicts with the landing-page subpath |
| Default check frequency | On boot + 24h interval | More aggressive (1h) wastes bandwidth; less (weekly) means revocations take too long |
| Default install timing | Next launch, no auto-relaunch | Worth re-confirming — some users prefer "install + restart now" |
| Beta channel for v0 | No (stable only) | Add once 10+ outside users opt in |
| Update notification UI | Banner at HUD top vs Status bar pill | Banner is more visible but louder; status bar pill is subtler — pick during US-X impl |
| GitHub Actions vs manual | Manual for v0 | Switch to CI when releases hit weekly cadence |

## 15 · What lives outside the Conan repo

The `conan-updates/` R2 bucket. The Cloudflare Worker that templates the
manifest URL. The minisign secret key (1Password). The CI workflow when it
lands. Same pattern as the licensing's separate `conan-license/` Vercel
project — sensitive operational infra lives behind your team's access
controls, not in a public-readable repo.
